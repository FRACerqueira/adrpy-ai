# Pre-release audit

This is the full mechanics for a pre-release or hardening review. See "When this skill applies" above for the gate on *when* this runs -- this is the *how*, invoked once that gate is met.

**Decide the review angles first, before touching any code.** Before starting any review pass, propose the angles that fit the change actually being shipped in *this* project, and get confirmation before proceeding. There is no fixed template, and none should ever calcify into one.

**Calibrate against history before proposing, for any round beyond the first.** Reconstruct each front's own convergence signal instead of guessing or defaulting to "run everything again": count findings per front per prior round (a project's own `audit-finding`- AND `doc-drift`-classified decision-log entries, cross-checked against the real commit/test history — never trust a remembered summary over the artifact itself), and compute a simple trend per front with 2+ data points (declining / flat / worsening / insufficient data). Include `doc-drift` in the same count as `audit-finding`, not a separate one — it's the same shape of event (a review angle found something wrong and fixed it), just scoped to a durable doc instead of code directly; a front whose output that round happened to land as `doc-drift` is not "zero findings." Read front, severity, and the round number itself mechanically from each entry's structured `**Front:** ... | **Severity:** ... | **Resolution:** ... | **Round:** ...` line (see the decision-log skill) — `Round` is the authoritative value; never parse it out of `Front`'s own free prose, which may mention a round narratively but isn't guaranteed to use the same grammar entry to entry. This needs no new bookkeeping — recompute it each time from whatever the project already records (decision-log, git log), the same "always generated, never hand-maintained" discipline the decision-log skill itself uses for its own index. If several rounds' worth of work later reads as one coherent push in hindsight, the decision-log skill's `CYCLES.md` ledger is where that gets a name — never a reason to invent a second numbering scheme here.

**Show this calibration automatically the moment a round closes, not only silently before proposing the next one — but only once there is a prior round to compare against.** As soon as the user confirms a round is closed, generate and display the count / highest-severity / severity-weighted-score / Direct-Escalated-Retraction table for every front that ran in it — don't wait for the next round to be proposed to surface it. Skip this entirely when the round just closed is the first round of a brand-new audit effort with no prior round or cycle anywhere in the project's history to set alongside it — a table with one data point and nothing to compare it to isn't a calibration, it's noise; the very first "beyond the first" round is still where this starts applying, per the existing calibration rule above. Once there is at least one prior round, default the table's own scope to two spans only: the still-open cycle's own rounds (every round since whichever `CYCLES.md` entry, if any, is still unclosed, or every round since this audit effort's own start if no cycle has been named yet) and the single most-recently-closed cycle, shown alongside it purely as one point of outside comparison. Never the project's full historical round-by-round table by default — most of that history covers unrelated scopes (a different cycle, a different area of the codebase) and adds noise to the one decision actually in front of the user right now: does *this* area need another round. Close the table with a one-line footer noting that the full cross-cycle history, back to the project's own first round, is available any time on request — but only ever shown on that explicit request, never by default.

**Render every calibration as a table, not prose.** Whenever this skill has you show counts/severity/score/resolution data — the automatic post-round display above, or any later calibration shown before proposing a further round — output a markdown table (one row per front, or per front-per-round when the round breakdown itself matters) with columns for count, highest severity, the severity-weighted score, and the Direct/Escalated/Retraction tally, followed by a short conclusion (2-4 sentences) interpreting what the table shows. Never narrate the same numbers as inline prose sentences instead of a table — a table is what lets the numbers be scanned and compared at a glance, which is the entire point of calibrating before proposing a round; prose defeats that even when every number in it is correct.

**Severity is context for the human's read, never an automatic verdict.** A raw per-round count can mislead (a single High can matter more than many Lows) — surface, alongside the count, the highest severity present that round, plus an informational severity-weighted score (default **Low=1, Medium=3, High=8** — a recognizable planning-poker-style scale, not an invented ratio) purely to show shape/direction across rounds for the *same* front. Neither the count nor the weighted score decides anything by itself — whether a front is "converged enough," should go dormant, or needs another round is a judgment call that belongs to whoever owns the project's risk appetite, made fresh each time in light of the indicator, never pre-bound by a formula or a threshold agreed days earlier. State the indicator; don't let it vote.

**A finding's `Resolution` field (Direct/Escalated/Retraction, see the decision-log skill) is a second, independent indicator — orthogonal to severity.** Severity/count answer "how much residual defect is left"; the resolution ratio answers a different question, "how settled is the project's own vocabulary for fixing this class of thing" — a front can stay unconverged by count while its fixes increasingly resolve `Direct` (against an already-established pattern) rather than `Escalated` (a fresh design call), which is real evidence the codebase's own conventions are maturing even while bugs keep surfacing. Surface the round's Direct/Escalated/Retraction tally alongside the severity indicator; same rule applies — it informs the human's read, it doesn't decide anything. A `Retraction` is the one value worth flagging on its own regardless of ratio: it means a previous round's `Direct` fix followed a pattern that has since been reversed, which is itself worth noting as residual instability in the *pattern*, not just the code.

**The reason for 1/3/8, if the weights are ever revisited:** the property that actually matters is the *ratio* between tiers, not the tiers' familiarity — the gap must stay wide enough that no realistic accumulation of low-severity findings can numerically match one high-severity finding, or the score quietly defeats the exact problem it exists to solve. Check any candidate scale against this test before adopting it: how many Lows does it take to equal one High? Under 1/3/8, it takes 8 — an unlikely volume in one round. A near-linear/arithmetic scale (e.g. 2, 5, 8 — equal +3 steps) fails this test badly: only 4 Lows (4×2=8) already tie a single High, letting a pile of trivia numerically pass as equivalent to one serious defect. Prefer a scale with widening (geometric-ish) gaps between tiers over one with equal or narrowing gaps, and re-run this same divide-and-check arithmetic against the new numbers before swapping them in.

Propose them in this shape — typically two to four candidates:

```
Proposed review angles for [release / change]:
1. [Angle] — why it matters here: [one line tied to this change in this codebase].
   Pass would read: [files, layers, or surfaces].
2. [Angle] — why it matters here: [...].
   Pass would read: [...].
Confirm, swap, or add before I start.
```

Answer "which pillars apply this time?" fresh, every time, for every project. As a pure illustration of the *output* of that question, never as a default input to it: one past project settled on three independent passes — concurrency and shared-state correctness, documentation-versus-code accuracy, and operational viability under real failure conditions — because those fit what that specific codebase did. A different project, or a different kind of change (a security-sensitive integration, a data migration, a public API redesign, a performance-critical path, a UI-heavy feature), calls for different angles entirely. Do not open with those three, and do not treat them as the list to trim down from.

**If there's no answer, the audit is blocked, not defaulted.** Say you're waiting on the angles. Never start passes on angles you assumed, and never quietly fall back to a previous project's set.

**Mechanics, once the angles are agreed:**

- **Keep passes genuinely independent.** No pass sees or is anchored on another's conclusions. Concretely: separate agent invocations that don't share transcript context, each given only the angle it owns and the code, with none told what the others found or are looking for. Run them in parallel where the tooling allows. If the tooling can't isolate them, say so rather than presenting sequential passes as independent ones.
- **Merge afterward, and report disagreement as disagreement.** Where two passes reach conflicting conclusions about the same code, present both with their reasoning; don't reconcile them into a single confident answer unilaterally. Deduplicate identical findings, but keep every distinct one attributed to the pass that raised it.
- **Fix findings via a red/green protocol** wherever reproducible: reproduce the problem with a failing check first, confirm it fails for the reason believed, then fix and confirm it passes. For non-reproducible findings, state explicitly why red isn't achievable and what was done instead (a targeted check of the guard itself, a code read of every caller).
- **Close the class, not the instance.** Once a bug pattern turns up once, search the whole codebase for sibling occurrences before considering the finding closed, and fix them together. State the search actually run — the pattern and the scope — so the claim is checkable, and list what it matched, including a bare "no other occurrences" when that's the honest result. Fixing only the spot first noticed, or asserting the class is closed without a search anyone can re-run, is not sufficient. This applies to the audit's own scaffolding too — a rule missing from one pass among several near-identical ones is the same class of bug as a fix missing from one file among several near-identical ones.
  **Define the class by the invariant being violated, not by the shape of the bug already found.** Before searching for siblings, state in one sentence what invariant was actually broken. A syntactic sibling search — grepping for the repaired function/call-site pattern — only finds bugs that share that exact shape. A semantic invariant is violated by *every consumer of the same concept*, which can be a different function entirely, reached through a different call path, with no textual resemblance to the line that was fixed — finding those requires walking the call graph/data flow from the invariant outward, not a grep for the symbol already patched. Treat "my own search found nothing else" as provisional, not as proof the class is closed — the check that actually validates it is an independent pass (a different front, a later round) probing the same area on its own terms.
  **Turn the closure claim into a checkable artifact, not a memory to rely on later.** Name each class-closure claim and each "checked, not a bug" verdict as its own line in the round's consolidated report, distinct from newly-found issues, and hand any still-open ones to whichever pass runs next in this area as a named verification target — not folded silently into "re-run the same angle." Prefer a search stated as an actual re-runnable query (a grep/AST pattern someone else can execute verbatim) over a hand-curated list, but its limit is a real one: re-running the same query only re-checks the dimension of the invariant it already covered, not a different dimension that happens to touch the same code.
  **When a finding's root cause is a small, reusable helper or pattern that plausibly exists outside the round's own currently-confirmed scope**, treat that as a trigger to re-examine whether the round's scope boundary still holds, not as evidence for a future round to rediscover independently — either widening the round's own scope on the spot when the fix is small and unambiguous, or naming a new, explicit follow-up front for the wider footprint.
- **When a round's findings require fixes across more than one file, validate the fix order against the codebase's real structure before starting, not just each fix's own outcome.** Findings that share logic a naive ordering would duplicate, or assign to only one fix when several need it, are the audit-round version of a sequencing error — with a higher cost here, since several findings' fixes are in flight at once. State the check actually run (which files were read, which import/module boundary was confirmed) as its own named line in the round's report, the same as a class-closure claim above.
- **A fix that widens what a function recognizes, or narrows what it rejects, must enumerate what it newly admits or excludes as part of closing that same fix** — not left for a later round to discover from a visible symptom. Closing an omission changes the function's own boundary, which can newly admit inputs nobody intended; check that blast radius before considering the fix closed.
  **That enumeration needs a positive control chosen adversarially, not just a negative one.** A test proving the bug case is now blocked is not the same claim as a test proving the boundary case still succeeds — the input that is genuinely valid for the invariant the fix protects, but comes closest to failing the specific check the fix now runs. A full green test suite does not satisfy this — a regression here is exactly the kind existing tests were never written to catch, since the fix changes what the function now rejects, not what it already covered.
- **A fix that hands an existing predicate or helper a new, higher-stakes decision inherits that predicate's own unverified scope in either direction — too loose or too strict.** Reusing it because it already existed and worked adequately for its original purpose is not the same claim as it being correctly scoped for the new one: re-verify its exact boundary against the real reference source, at the strictness the new role demands, before trusting it there. Record this re-verification as its own named line in the round's report, the same as a class-closure claim — not left implicit in the fix's diff.
- **Agree the stopping criterion before the last round, not after seeing the result.** Stop when a front stops finding anything new, not when a fixed round count decided in advance — with no information about the real project — is reached. Fronts don't converge in lockstep: one may flatten out after two clean rounds while another keeps finding thinner residue for longer, or turns out to be the kind of pillar (e.g. a live measurement) that never "converges" and stays on as an ongoing check instead.
- **Never accept an audit round's report as fact without confronting its strongest claims against the raw execution log** — the actual run, not the summary an agent wrote about its own work.
- **Clearing a finding as "correct, not a bug" needs the same evidence bar as confirming one — never by analogy alone.** A "this matches the reference behavior" or "this sibling already handles it, so this one must be fine" verdict is exactly as failure-prone as a false bug report, and harder to catch afterward since nothing gets fixed or tested as a result. Trace *this exact path* against the ground truth before writing a finding off.
- **When the risk justifies it, run at least one front on a different model family, not only a different tier within the same one.** Fronts on the same model, even with different instructions, tend to share the same blind spots; escalating tier within a family is the fallback when family diversity isn't available, not a substitute for it.
- **Escalate trade-offs instead of deciding them.** A finding whose fix carries a trade-off (a breaking change, a measurable performance cost, a design decision with more than one defensible answer) goes back to the project owner with the options and the cost of each spelled out. Don't implement a preferred option while waiting for the answer, and don't bundle a trade-off decision into an unrelated fix's diff. Findings whose fix is unambiguous — a clear defect with one correct repair — just get fixed and reported.
- **For an audit or other long-running task spanning multiple sessions, an ephemeral `/TODO` folder at the project root may hold working notes** — viability findings, the change plan, convergence-of-results tracking across passes. This exists only for the duration of that audit/task, is not a standing project document, and doesn't replace ADRs, committed docs, or the findings actually reported back. Remove it when the work concludes. Don't create it for routine changes or short tasks.

**When the audit ends.** It ends when the agreed passes have all reported, their findings are fixed or escalated, and the project owner says the audit is done. It is not a cadence that continues on its own: don't propose another round unless something new is shipping or asked for. If a round's own findings suggest a further angle is worth running, raise it as a proposal under the angle-confirmation step above rather than starting it. This same "the owner says it's done" moment is also the signal the decision-log skill's `CYCLES.md` ledger uses to close (and become nameable) a cycle spanning the rounds just finished — see that skill's "Cycles" section; propose a name grounded in what the closed rounds actually found, don't leave it for later.

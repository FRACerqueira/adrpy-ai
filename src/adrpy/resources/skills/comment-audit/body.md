# Comment audit

A deliberate, on-demand sweep of a project's comments and doc-comments — distinct from the
running commentary that normally accumulates on code and XML docs during a work session (which
is expected and useful *while the work is in flight*: see the rule below on what "in flight"
comments look like). This skill is what turns that trail back into a clean, durable surface once
the work behind it has landed.

## Hard constraints

- **Comments and doc-comments only.** Never change code logic, signatures, names, or
  formatting of non-comment lines in this pass. If a comment only exists because the code
  it sits on is genuinely confusing, keep the comment, flag it in the report as a refactor
  candidate, and move on — fixing the code is a separate task the project owner asks for separately.
- **Batch by top-level directory or module, not the whole repo in one shot.** Enumerate the
  target file set once (see below), group it by logical unit (top-level source directory, or
  project (csproj/package) boundary if that's finer-grained and more natural for this repo),
  process one group at a time, emit that group's report, and **stop and wait for an explicit
  go-ahead before starting the next group.** Don't chain groups automatically — a misjudged
  classification should surface after one directory's worth of damage, not the whole tree's.
- **Never commit.** This pass produces a working-tree diff for the project owner to review and commit
  themselves, same as any other edit.
- **Source-controlled files only.** Enumerate with `git ls-files` (or the project's own file
  list convention if it has one) so build output, `node_modules`/`bin`/`obj`/`dist`, and
  anything already gitignored are never touched. Skip any file whose header marks it
  auto-generated (`<auto-generated>`, `@generated`, `DO NOT EDIT`, etc.) — report it as
  skipped, don't open it.

## Building the file set

1. `git ls-files` scoped to the target path (whole repo by default, or a path the project owner named).
2. Filter to source file extensions the project actually uses (infer from what's present —
   don't hardcode a language list).
3. Group by top-level directory under the target path (or by project/package manifest, when
   that's the more natural unit — e.g. one group per `.csproj`, one per npm workspace).
4. Present the group plan (group name → file count) before touching anything, so the project owner
   knows how many checkpoints to expect.

## The six-step pass, applied to every comment and doc-comment

Applied in order; the first rule that matches decides the comment's fate.

1. **Narration** — restates the code, describes steps, restates a name/type/signature, marks
   a block end. → **Delete.**
2. **Change narration** — addressed to whoever reviewed the diff that introduced it, not to a
   future reader of the file: "fixed X", "added per feedback", "now uses Y instead of Z",
   "as part of this round", a reference to a specific audit round/finding code/phase number
   that is now closed, or to a plan/checklist doc that no longer exists. Test: would this
   sentence make sense to someone opening the file cold, a year from now, who never saw the
   session that produced it? If not → **delete.** That history belongs in the commit message
   or the audit record, and it already lives there.
3. **Moving target** — points at something that drifts or gets superseded instead of encoding
   the substance itself: a spec section number, "see the design doc", "per the requirements".
   → **Delete** if the point never needed a comment, or **rewrite** to state the substance
   inline. The one exception is a genuinely durable, stable-address reference — see below —
   which is kept as a breadcrumb, never as a substitute for the substance.
4. **Bloated or misplaced *why*** — carries real rationale but at the wrong length or the
   wrong location. Trim to the one non-obvious fact a reader needs at that exact line, in the
   fewest words; split a header block into comments placed next to the lines they each
   govern; if a maintained doc already carries the system-level narrative, delete the inline
   copy rather than leaving a pointer to it. Never shorten a comment at the cost of
   information a maintainer needs to avoid re-breaking the thing it's warning about.
5. **Stale** — describes behavior or code that no longer exists. → **Delete**, or correct it
   if the underlying point still holds and is worth keeping. A wrong comment is worse than no
   comment.
6. **Survives all five** — a non-obvious constraint, a contract the signature can't show
   (units, ranges, failure modes, side effects), a deliberate deviation from the obvious
   approach, a cross-file sync obligation, or the source of a non-trivial algorithm. →
   **Keep**, worded as tightly as it already is. Don't reword a comment that's already
   minimal — churn on a good comment is noise too.

Asymmetric bar: when genuinely unsure whether something is a load-bearing *why*, keep it —
wrongly deleting a real warning costs more than leaving one mediocre comment. When unsure
whether something is narration, delete it — narration is the default failure mode of a
comment added mid-session, and it's cheap to be wrong about.

TODO/FIXME markers are kept without needing an issue ID, with two exceptions: one that
describes work now visibly done (rule 5, delete), and one that reads as deferred work
disguised as a marker on a path that plausibly should already be handled — keep it, but flag
it in the report rather than silently deleting or silently accepting it.

**Exception — never on public API surface.** The rule above is for internal/private
implementation. A TODO, FIXME, or open design question attached directly to a public
declaration (a public type, an interface member, an exported function/class) is a different
case: it doesn't just note deferred work, it attaches visible uncertainty to a contract
consumers already read and call. This applies whether the marker sits as a `//` line next to
the declaration or as text inside its `///`/docstring block — proximity to a public
declaration is what triggers this, not which comment syntax carries it. Never leave this kind
of marker in source on a public declaration, even when the question it captures is genuine.
Delete it, and surface it once in that batch's report as an **unresolved public-API design
question** — let the project owner decide where it belongs (an issue, an ADR draft, or nowhere until
it's resolved), instead of embedding the uncertainty in the shipped interface itself.

## Durable vs. ephemeral references

The recurring judgment call in rule 2/3 is whether a reference is a stable address or a
snapshot of process state. Use this test, not a fixed vocabulary — it holds across languages
and project conventions:

- **Durable (keep as a breadcrumb):** an identifier with a permanent, resolvable address that
  doesn't move once assigned — an ADR/RFC number, an issue/ticket ID, a permalink, a
  maintained doc at a stable path that lives and updates alongside the code. These name *a
  decision*, not *a moment in the work that produced it*.
- **Ephemeral (rewrite or delete):** anything that names a moment in the process instead of a
  decision — an audit/review round number, a finding/ticket code from a now-closed tracking
  pass, a phase or step name from a plan, a reference to a plan/checklist file that has since
  been deleted or archived, "as of the current fix", a spec section number (sections get
  renumbered; the requirement itself doesn't).

A durable reference is still only a breadcrumb, never the explanation itself: `// see
ADR-014` without the substance is as useless as `// see the spec`. Keep the ID *and* the one
line of substance it backs, per rule 4.

### Optional per-project refinement

If the target repo has `.claude/comment-audit-patterns.md`, read it before starting and merge
it with the heuristic above — patterns listed there don't replace the general test, they
resolve specific cases the project knows are exceptions to it (e.g. an internal ID scheme
that looks like a round number but is actually durable, or a doc path that looks stable but
is actually a snapshot). Format:

```markdown
## Durable
- ADR-\d+          # architecture decision records, permanent once numbered
- JIRA-\d+

## Ephemeral
- \[Round \d+\]     # internal audit-round tags, not part of the public history
```

No file present → proceed on the generic heuristic alone. Don't create this file
unprompted; if a batch's report surfaces a recurring pattern the heuristic keeps getting
wrong for this project, say so and offer to write it, but let the project owner decide.

## Doc-comments (XML doc, docstrings, JSDoc, etc.)

The same six rules apply inside `///`/`"""`/`/** */` blocks exactly as in line comments,
including the durable-vs-ephemeral test for anything they reference. Two additions specific
to doc-comments, because they're often public API surface:

- A one-line summary on a public type/member/endpoint is legitimate even when the line below
  it is self-explanatory — other consumers read the doc without reading the body. This is not
  narration; don't delete it under rule 1.
- Condensing a doc-comment to that one-liner is only valid when nothing beyond signature
  restatement is lost. A doc-comment that states preconditions, valid ranges, thrown
  exceptions, side effects, or invariants is a contract, not narration — trim its wording,
  never its content.

## Report (per batch, and a final cumulative summary after the last batch)

1. **Counts** — comments/doc-comments deleted, rewritten, kept-as-is, per file.
2. **Flags** — anything out of scope for this pass: comments compensating for confusing code
   (refactor candidates), deferred-work TODOs, comments whose correctness couldn't be
   verified from the surrounding code alone (kept conservatively).
3. **Judgment calls** — borderline durable/ephemeral or keep/delete decisions, one line each,
   so the project owner can overrule before moving to the next batch.

Keep it brief — don't enumerate every deleted narration comment, that's the point of the
pass, not news. End every batch's report with the next group's name and file count, and wait.

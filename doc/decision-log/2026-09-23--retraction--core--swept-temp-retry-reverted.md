# atomic_write no longer rewrites and retries a temp file a concurrent sweep removed

Retracts the atomic_write part of 2026-09-23--audit-finding--core--flags-temp-recovery-sweep-warning-log-retry, which said a temp file removed before os.replace is rewritten and retried. Reverted in 2e5854f (R1a): a retry cannot tell a clock-skew sweep from a lock that was already reclaimed, so retrying could commit a write whose lease another call now holds. The remaining limitation (a network share whose server clock runs behind lets a concurrent call sweep an in-flight temp) is documented in atomic_write, per calling command (P3a). The rest of that entry (repeated and swallowed flags, the sweep warning, the log retry) stands. Visibility: the write fails with the calling command's own code -- io-error, or supersede-write-failed / reject-own-write-failed-after-predecessor-reverted as a partial success -- and a detail naming the file; nothing retries silently.

Architectural review (Round 43): the reason given here, a lock lease another call may hold, no longer applies: adrpy has no lock (ADR001). The revert stands for a simpler reason: only a second adrpy command running in parallel sweeps another's in-flight temp file, and the single-owner model rules that out. The codes named here changed: a two-file write whose second commit fails reports `multi-file-write-partially-applied` (data.applied, data.pending, data.repair); `supersede-write-failed` and `reject-own-write-failed-after-predecessor-reverted` no longer exist.

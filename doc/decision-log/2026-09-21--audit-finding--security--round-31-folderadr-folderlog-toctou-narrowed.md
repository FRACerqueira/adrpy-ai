# Round 31: narrow a TOCTOU window in the round-30 alias guard (reject_aliased_repo_folders)

**Front:** Security | **Severity:** Medium | **Resolution:** Escalated | **Round:** 31

The round-30 fix (reject_aliased_repo_folders, resolving folderadr/folderlog for real and comparing the resolved paths) closes static, pre-planted junction/symlink aliasing at all 3 call sites (init.py, config.py, log.py), checked once before real use. A dedicated round found this check-then-use pattern itself leaves a TOCTOU window: a filesystem-level actor with write access, actively co-resident and synchronized to a live adrpy log/init/config invocation, can swap a genuinely non-aliased folderlog for a junction onto folderadr after the check passes but before the directory is created/written into. Confirmed live and reliably winnable: 76% win rate (38/50) using a lightweight, syscall-only racer under natural (non-artificially-widened) timing, with the decision-log entry landing physically inside doc/adr and the command reporting success:true.

This is a narrower class than every prior High finding on this front: it requires an attacker actively racing a specific live invocation, not merely a statically hostile repository shipped once -- a materially stronger capability requirement, and one ADR001 already documents as a residual limit no advisory, non-atomic userland lock can fully close. Severity assessed as Medium, not High, on that basis.

Two other sub-questions from the same round closed with no gap found: (1) the mkdir-before-check ordering in init.py is harmless (mkdir is idempotent/exist_ok=True, writes no content, and mirrors an already-accepted, already-documented pattern elsewhere in this codebase); (3) a hand-edited config that aliases folderadr/folderlog stays dormant until the next log/config call, which always re-validates before any real use -- no command reads folderlog without going through the guard.

Fix (escalated: documented as a residual risk vs. fix now, and which fix shape, both resolved by the repo owner via explicit trade-off questions): re-verify via reject_aliased_repo_folders a second time, immediately before each call site real commit (log.py before log_dir.mkdir, config.py before the config write, init.py before the config write) -- mirrors this project own established narrowing pattern for this exact class of gap (ADR001 part 3 / lock.verify_still_held, re-verified right before commit, not just before the operation starts). Not a formal atomic guarantee (a true fix would need a file-descriptor-based primitive, POSIX and Windows handled separately, judged disproportionate engineering for a Medium-severity, attacker-must-be-co-resident finding) -- narrows the window to the same order of magnitude as that existing pattern.

Verified via red/green at all 3 call sites: a new test per site (test_log.py, test_config_command.py, test_init.py) plants a real Windows junction mid-call (via monkeypatch on a function that runs between the two checks), confirmed to fail for the predicted reason against the unfixed code (DID NOT RAISE CommandError -- the write silently succeeded into the aliased directory), then confirmed green after the fix. Full suite: 1025 passed, 3 skipped, 1 xfailed. ADR007V01 revised (round 31) to record the narrowed residual risk.

Architectural review (Round 43): the second, pre-commit check this entry added was removed together with the lock. Under the single-owner model (ADR001) a process actively racing a specific invocation on the same working copy is outside what adrpy defends against, like two adrpy commands run in parallel. Each of the 3 call sites checks once, before real use: the round-30 static aliasing stays closed, and the window measured here is accepted, not narrowed. ADR007V01 records the same; the mid-call junction tests of this round went with the check, the round-30 tests remain.

# Guard's own data.changed_fields claim and README's defaults wording drifted from round-19 code

**Front:** Usability audit | **Severity:** Medium | **Resolution:** Direct | **Round:** 20

An independent round-20 usability pass on round 19's own documentation changes (the ADR004V02 scheme-scoped guard) found two drifts, both re-derived from the actual code, not just compared page-to-page. (1) config.py/init.py's describe() (and their .md mirrors) claimed data.changed_fields on the guard's blocked-error 'names every guarded field this call touched' -- but the code (core/lifecycle.py) actually returns only the scheme-scoped subset that is genuinely blocking; a call changing a blanket field plus migrationpattern on a current-scheme-only repository gets only the blanket field back, even though migrationpattern was also touched and also failed to commit (the write is atomic). Confirmed the code's own behavior is the more useful, actionable one (matches the free-text error message, tells the caller exactly what to remove to make the call succeed) -- fixed the docs to match the code, not the other way around. (2) README.md's defaults paragraph used vaguer language ('not every field, just the ones that matter most day to day') than help.py's own precise enumeration ('template, migrationpattern, headerdisclaimer, the 11 header-row labels, and the plugin fields'), never naming migrationpattern specifically -- notable since migrationpattern just became a permanently-blocking guarded field in this same round. Fixed README to name the same omitted fields help.py already does. Both fixes carried into round 20's own ADR004V02 revision (the separator-reclassification correction), so the guard's final documented behavior (config.py, init.py, their .md pages) reflects the corrected scoped-count/changed-fields semantics too, not just the corrected separator/migrationpattern scoping.

# Shared-doc writes now reported in installed; a blocked shared doc now stops the stub providers that reference it

**Front:** Round 36: re-verification front | **Severity:** High | **Resolution:** Direct | **Round:** 36

Round 36's re-verification front (a fresh, whole-file adversarial pass on installer.py after 3 consecutive rounds of layering) found two real bugs introduced by Round 35's own reordering fix. High: a successful shared-doc write never appeared anywhere in the result, even in the plain happy path -- a caller checking installed for confirmation of what was actually written on disk would have missed it entirely, reproduced via a plain copilot install showing installed containing only the copilot row despite the shared doc also being created. High: a blocked (foreign/drifted, no --force) shared-doc write had no effect on whether a stub-mode provider's own file still got written pointing at it -- reproduced concretely: pre-seeding a foreign shared doc, then installing agentsmd, reported a clean install success (agentsmd in installed) while the AGENTS.md block's own reference pointed at content that was never verified or regenerated. Fixed: shared-doc writes are now appended to installed (provider shared-doc), symmetric with remove()'s own reporting. A new shared_doc_blocked flag, computed once per skill right after the shared-doc write attempt, gates every stub-mode provider (copilot, agentsmd) in the same skill's provider loop -- any of them is skipped with reason shared-doc-blocked instead of proceeding when the shared doc itself was refused. 3 new red/green tests (2 confirmed failing against the pre-fix code for the predicted reason), ~15 existing tests updated to the new, more precise installed/skipped shape now that the shared-doc row is independently reported.

# _read_header_bytes was O(n^2) with no size cap, reopening the unbounded-read DoS class via a different path

**Front:** Security audit (round 27, 6th pass -- systematic review, part B: I/O, concurrency, orchestration) | **Severity:** High | **Resolution:** Escalated | **Round:** 27

Round 27 (Security's 6th pass, systematic review of atomic_write.py, io_retry.py, lock.py, lifecycle.py, decision_log.py, install_config.py, registry.py, warnings.py, errors.py, output.py) closed 2 findings, both live-reproduced. (1) HIGH: core/lifecycle.py's _read_header_bytes -- the shared helper behind read_header_lines/read_header_lines_with_report, itself the round-26 fix for explore's own unbounded read -- had no size cap and re-scanned its ENTIRE accumulated buffer for real newlines on every 4096-byte chunk (O(n) regex work per chunk, O(n^2) total), plus `buffer += more` (O(n) copy per chunk, also O(n^2) total). A file that never accumulates 12 real newlines -- a single unstructured blob, plausible for corrupted content or a file from an untrusted migrated repo -- made the loop run to EOF, quadratically re-scanning and re-copying the file's entire content. Confirmed live: 1MB=0.6s, 2MB=2.5s, 4MB=10.9s (~4x per doubling); a 4MB adversarial sibling made family_members alone take 10.1s. Reachable via family_members (every per-file mutating command: approve/reject/undo/supersede/version/revise, all while holding the repository lock) and migrate's own repo-wide scan phase (every recognized .md file in the whole decisions folder). Fixed two ways: counts newlines within each newly-read chunk only (no more whole-buffer rescanning), and caps the total read at 4 chunks (16KB) regardless of newline count -- a genuine header is always a few KB at most (the config schema's own field-length limits keep it there), so the cap can never truncate a real header, only a pathological one, which then correctly falls through to parse_header's own existing adr-file-too-short handling. Confirmed live post-fix: the same 4MB file now reads in ~0.012s, and a 100MB file takes the identical ~0.012s (bounded regardless of size). (2) MEDIUM: decision_log.py's _parse_entry read the whole entry file (path.read_text().splitlines()) even though only lines[0]/lines[1:5] are ever used, unbounded by any field-length limit on --body/--summary/--front/--reopenwhen -- a single oversized entry made every future `log` call re-pay the cost of reading it in full, scanning the whole directory. Fixed by switching to the same bounded read_header_lines (count=5) the rest of the codebase already relies on. Both mutation-confirmed. Also re-verified (not just trusted): the round-26 explore.py fix is still intact; lock.py's round-25 math.isfinite() fix is still present and correct; verify_still_held() precedes every atomic_write_* call across every lock-acquiring command, not just the two previously spot-checked (approve/supersede).

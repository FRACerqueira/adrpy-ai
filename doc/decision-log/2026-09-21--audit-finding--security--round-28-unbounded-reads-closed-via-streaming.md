# 4 unbounded whole-file reads closed via real streaming (ADR006V01) or a fixed cap; 2 further defects found and fixed during that same implementation

**Front:** Security audit (round 28, 7th pass -- systematic review split by invariant, invariant C: bounded reads/writes everywhere) | **Severity:** High | **Resolution:** Escalated | **Round:** 28

Round 28's systematic pass, split by invariant instead of directory (per an explicit request after round 27's directory-split proved to still miss cross-cutting gaps), covered 'every read of file content has a real, enforced upper bound' across the whole codebase. Found 4 unbounded reads: read_target's primary read (approve/reject/undo/supersede/version/revise, plus reject's predecessor read) and migrate.py's per-candidate legacy read both loaded whole-file content with no cap (live-measured: 150MB file -> ~300MB traced peak), read_config_text (core/config.py, every command's own config load plus init/installconfig --seed) likewise (100MB -> 200MB peak), and lock.py's _read_lock the same shape, narrower reach. Fixed via ADR006V01: migrate.py and read_target's own body handling both switched to real chunked streaming (no cap needed at all, since a decision body has no schema-imposed size bound) via a new atomic_write_chunks helper; read_config_text and _read_lock got fixed byte caps (64KB / 4KB) after TEMPLATE_MAX_LENGTH=10000 closed the one previously-unbounded config field that made a tight config cap unsafe before. Two additional defects surfaced DURING this implementation, not from the original 3 audit passes, and closed in the same round: (1) _read_header_bytes's round-27 per-chunk newline count could double-count a CRLF straddling a 4096-byte chunk boundary -- fixed by rescanning the whole (still 16KB-capped) buffer each iteration instead of trusting an isolated per-chunk count. (2) The streaming refactor itself introduced a real regression, caught red/green before commit: moving the body read+write inside rewrite_status_field/mark_superseded/version/revise/migrate meant a real body's streaming duration reopened the exact check-to-commit lock window ADR001 requires kept shut -- live-reproduced (a lock stolen mid-stream was silently ignored, file committed as Accepted anyway) before fixing via a second lock.verify_still_held() call as the last step of each streaming chunk generator, right before atomic_write_chunks's own commit. A follow-on gap in that very fix was then found independently (not by the same pass that wrote the fix): atomic_write_chunks only cleaned up its orphaned temp file on OSError, so the new LockLostError-from-inside-the-generator path leaked a .tmp file (harmless -- swept up by the next command's own pre-lock cleanup_orphaned_temp_files pass within 30s, never corrupting anything -- but a new, previously-impossible exception surface the streaming refactor opened) -- fixed by widening the cleanup to any exception, not just OSError. Suite: 997 passed, 3 skipped, 0 failed. 29 files touched (see ADR006V01 for the full list).

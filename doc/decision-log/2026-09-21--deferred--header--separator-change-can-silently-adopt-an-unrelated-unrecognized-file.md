# A --separator change can silently recognize a previously-unrelated file as a decision

**Reopen-when:** the next audit round scoped to ADR004/decision-recognition runs (whether reactively triggered or as part of a broader pre-release audit), or before any real PyPI release of this package -- whichever comes first

A narrow Stability verification pass on round 20's own fix (confirmed that fix itself correct -- see the full truth-table verification in the pass's own report) surfaced a distinct, pre-existing gap while investigating further, confirmed live independently (not just reasoned about). The existing-decisions guard (core/lifecycle.py's reject_status_or_separator_change_if_decisions_exist) only ever scans for decisions ALREADY recognized under the OLD config before deciding whether a change is safe -- it has never checked the opposite direction: whether the change would make a file that is CURRENTLY UNRECOGNIZED (by either naming scheme) become newly recognized. Reproduced live: an unrelated, hand-written .md file with no relationship to the decision lifecycle (never created via 'new', not matching any naming scheme under the current separator) sits in the decisions folder; changing --separator to a character that happens to appear in that file's own name is ALLOWED (the guard's pre-change scan finds zero existing decisions, so nothing blocks it); the very next scan (explore, next_number, etc.) silently absorbs that file as a genuine current-scheme decision, with zero warning, corrupting next-number allocation and title-uniqueness checks for every subsequently created decision. This is NOT a regression introduced by round 19 or round 20 -- V01's original blanket check has the identical blind spot (it also only ever scanned recognized decisions under the old config), so this has been present since the guard was first written; it was only found now because a verification pass investigated one level deeper than the specific question it was asked. Checked the sibling case for migrationpattern (same mechanism, same live-confirmed outcome) and it is NOT a bug there -- recognizing pre-existing hand-written legacy files via a migrationpattern change is that field's own documented, intentional purpose (see ADR002V01 and core/naming.py's own module docstring); separator has no equivalent 'intentional adoption' semantics, so an unrelated file being silently absorbed via a separator change is unintended in a way the migrationpattern case is not. Checked the only sibling guard with the same 'keyed on old-config recognition' shape (reject_folderadr_change_if_decisions_exist) -- confirmed clean, its own harm model (a recognized decision becoming invisible) has no unrecognized-to-recognized analogue. Severity assessed as Medium-to-High by the finding pass: silent, zero-warning identity assignment to a file the user never created as a decision, with concrete downstream corruption potential, though not destruction of any existing real decision.

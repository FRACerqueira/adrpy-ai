# front/severity/resolution/reopenwhen skipped delimiter and closed-set validation

**Front:** Usability audit + Test-Adequacy audit (independently, 2 fronts) | **Severity:** High | **Resolution:** Direct | **Round:** 12

Two related gaps in the same four fields. First: describe() documented --severity as one of Low/Medium/High and --resolution as one of Direct/Escalated/Retraction, matching this project's own established closed-set-argument pattern, but run() never actually validated either -- any string was accepted and written verbatim. Second: --front/--severity/--resolution/--reopenwhen never went through reject_embedded_delimiter, unlike --scope/--summary -- despite being embedded directly into the entry's own '|'-delimited structured line and into INDEX.md's own '|'-delimited table row. The Test-Adequacy front confirmed this empirically: passing an embedded newline through --front wrote successfully, split the structured line across two physical lines, and caused _FRONT_SEVERITY_RE to fail matching on the next parse -- next_round silently returning a wrong value for the following call, and regenerate_index silently emitting a blank row for the corrupted entry. Fixed by adding validate_severity/validate_resolution (new log-severity-invalid/log-resolution-invalid codes) and applying reject_embedded_delimiter to all four fields, the same as scope/summary already had.

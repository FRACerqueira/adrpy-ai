# installer.py's reads now retry a transient PermissionError; retried writes now surface a warning

**Front:** Round 35: resilience front | **Severity:** Medium | **Resolution:** Direct | **Round:** 35

Round 35's resilience front found installer.py was the only reader in the project that never used core/io_retry.py's read_with_permission_retry -- a single transient PermissionError (a Windows 'pending delete' window under a concurrent reader) failed the whole install/remove/list call outright, where every other reader (core/config.py, core/lock.py, core/lifecycle.py) already absorbs it via the same shared helper. Confirmed empirically: a mocked single transient PermissionError on one drift-check read raised immediately with no retry loop at all. Through the real CLI this still surfaced as a clean io-error (the exception-handling contract held), but the call failed outright on a blip the rest of the project already tolerates. Fixed via a new _read_text() helper used at all 9 read call sites. Also found and fixed the write-side mirror: a write that only succeeded after absorbing transient contention was silently discarded instead of surfaced via core.warnings.retry_warning, unlike every core-CLI write site (cli/new.py, cli/log.py, cli/installconfig.py, etc., which all capture atomic_write_text's own attempt count). Fixed at all 4 atomic_write_text call sites. 2 new red/green tests confirmed failing against the pre-fix code for the predicted reason.

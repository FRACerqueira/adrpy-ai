# A stale (pre-lock) lenseq does not corrupt filename recognition

Round 5 stability re-run, Finding 7: every write command bootstraps config BEFORE acquiring the repository lock (necessary -- the lock's own location is derived from `folderadr`), so a concurrent `config` edit to `lenseq` between that read and the write could, in theory, let a file get built with a stale width. Investigated whether this could cause the file to become unrecognized by a later scan under the real (post-edit) config, letting `next_number` reuse a number.

**Confirmed NOT to hold:** `core/naming._ADR_PATTERN` matches variable-length digit runs (`\d+`), not a `lenseq`-specific width -- a stale `lenseq` only changes zero-padding cosmetically; the file stays fully recognized under any subsequent config's own `lenseq`. Recorded as a permanent regression test (`tests/test_naming.py::test_parse_any_filename_recognizes_a_file_built_under_a_different_lenseq`) per the project's own rule that an investigated hypothesis which doesn't hold becomes a test, not wasted effort -- this entry is the narrative counterpart, so a future session re-suspecting this finds the answer instead of reinvestigating.

# Status-label content could forge ADR004V01's own hidden marker and date, bypassing the guard's core promise

**Front:** Security audit (round 22, 1st pass -- new front, AI-agent-driven-input threat model) | **Severity:** High | **Resolution:** Direct | **Round:** 22

adrpy-ai's own README states it is designed for AI agents to drive through a shell tool, relaying potentially attacker-influenced strings without necessarily validating them first -- the round-22 calibration explicitly introduced Security as a new front on that basis (this repository's first security-focused audit pass). It found and I independently live-reproduced a HIGH severity vulnerability: reject_embedded_delimiter (core/security.py) blocked only '|' and line-break-like characters on the four status-label fields, but not '(', ')', '<!--', or '-->' -- the actual control characters of _parse_status_cell's own parsing grammar (core/header.py), which trusts the FIRST '(' and first ')' in a status cell to bound the date and then searches after it for ADR004V01's own hidden canonical marker. A hostile statusnew/statusacc/statusrej/statussup value containing a well-formed '(date)<!--Status-->' substring therefore forges a marker and date the tool never wrote. Confirmed live: a repository seeded with statusnew = '(20200101)<!--Rejected-->' had a decision created today (refdate 2026-09-21) read back as Rejected/2020-01-01 instead of Proposed/today -- directly undermining ADR004's own core promise that the marker, not the label text, is the untamperable source of truth. Fixed with a new function, reject_status_marker_forgery_characters (core/security.py), rejecting these four characters, scoped only to the four status-label fields (not the 11 header-row labels, which are never read by _parse_status_cell -- confirmed with a positive-control test that a header label containing '(' still succeeds) -- wired into parse_repo_config (core/config.py), the single validator both `config` and `init --seed` already converge on, so no bypass exists between the two entry points. describe() (config.py) and its .md mirror updated to document the new constraint. Mutation-confirmed: disabling the new check made 20 parametrized rejection-case tests fail for the predicted reason (DID NOT RAISE), while the positive control (header label) stayed green throughout. The Security pass also checked and closed four other threat vectors as already safe, with no fix needed: ReDoS in the three header-parsing regexes (empirically tested with 200-400k character adversarial inputs, all sub-11ms); path escape via separator/migrationpattern/folderadr (a closed whitelist, a regex-validated pattern, and resolve_within respectively); resource exhaustion via a symlink/junction loop (bounded by Windows' own reparse-point limit, pre-existing across every scan_decisions caller, not worsened by ADR004); and --seed bypassing config validation (both `config` and `init --seed` converge on the identical parse_repo_config validator).

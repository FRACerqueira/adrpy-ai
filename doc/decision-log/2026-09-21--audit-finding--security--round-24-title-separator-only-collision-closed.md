# A title made only of whitespace/_/- echoed raw by to_case, colliding with the filename separator and orphaning the file

**Front:** Security audit (round 24, 3rd pass, new territory beyond rounds 22-23) | **Severity:** High | **Resolution:** Direct | **Round:** 24

Round 24 (Security's 3rd pass) found and I independently live-reproduced a HIGH severity defect: core/casing.py's four to_*_case functions (to_camel_case/to_pascal_case/to_snake_case/to_kebab_case) all share a fallback -- 'if not words: return text' -- that echoes the RAW, untransformed input unchanged when word-splitting (on whitespace/'_'/'-') finds nothing left to transform, which happens exactly when a title consists ENTIRELY of those same whitespace/'_'/'-' characters (e.g. '-', '---', '___'). Neither existing title check caught this: reject_embedded_delimiter only blocks a title that is blank after stripping, and '-'/'---' are not blank; reject_filesystem_unsafe_title (round 23) only blocks `<>:"/\|?*` and control characters, none of which whitespace/'_'/'-' are. The raw echo then collides with the filename's own separator: confirmed live, `new --title "-"` with the default '-' separator created 'ADR001V01--.md', which naming.parse_filename can no longer recognize AT ALL -- the file is permanently unreachable by approve/reject/undo/supersede/version/revise (all fail filename-not-recognized with success:true never having warned anything was wrong), and its own sequence number is silently reallocated to the very next decision created (confirmed: a second `new` call reused number 1, producing two live decisions both claiming ADR001V01). `explore` is the one command that still lists the orphan, but with scheme:null/number:0/title:null -- visible, not actionable. Fixed with a new function, reject_title_with_no_case_transform_content (core/security.py), rejecting any title where removing every whitespace/'_'/'-' run leaves nothing behind -- the exact condition under which to_case's own fallback triggers. Wired into new/version/revise/supersede/migrate at the same point each already validates or re-reads title (same five call sites as round 23's own filesystem-unsafe-character fix), since the identical raw-echo risk applies wherever build_filename is reached: a hand-edited or migrated file's title (version/revise/supersede) or a raw legacy filename's title segment (migrate) can carry this shape exactly as easily as a live --title flag. describe() and .md mirrors updated for all 5 commands. Mutation-confirmed at all 5 integration points (removing each independently made its own dedicated test fail with DID NOT RAISE, then restored). Four other vectors checked and closed as safe, no action needed: unique_title_key's Unicode case-folding (tested 'Strasse' vs 'Straße' -- no collision, since the code only ever applies .upper()/.lower() per-word-character, never a full-word .upper() that would expand 'ß' to 'SS'); installconfig's own lost-update race (already explicitly documented and accepted as a deliberate, low-blast-radius trade-off in its own module docstring -- never corruption, only a lost update); template field body concatenation (the 12-line header is always parsed strictly positionally, lines[0:12] only, so template content -- even shaped like a fake header table -- lands only in the body and cannot forge the real header); numeric field overflow on lenseq/lenversion/lenrevision (naming.py's own module docstring documents the current-scheme regex is deliberately variable-length, not padded, specifically so a number outgrowing a shrunk config stays recognized -- an anticipated, already-handled case). Three items flagged as NOT fully checked this round, still open: lock-file content trust beyond token/timestamp parsing, help/describe() output under a tampered config, and an exhaustive sweep of every lossy-UTF-8-decode consumer for cross-file equivalence effects (the specific title-uniqueness angle was ruled out -- find_by_unique_title compares filename-derived titles, never header/body content -- but the sweep was not exhaustive).

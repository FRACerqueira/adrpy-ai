# supersede has no --title flag for the successor; ADR007V01 carries ADR003V01's own title as a result

**Reopen-when:** when a supersede --title flag is designed/implemented, or when this same title-inheritance friction recurs on a future supersede

While superseding ADR003V01 to create ADR007V01 (folderlog independence), discovered that `adrpy supersede` always carries the predecessor's own title forward verbatim into the successor -- confirmed reference-tool fidelity (cli/supersede.py: title is re-read from the predecessor's own filename segment, never a flag), with no way to give the successor a different title. This is a real design gap: a decision that legitimately changes in a way that warrants a new title (as ADR007V01 itself does -- its real content is about folderlog independence, but its own filename/header-table title field still literally read ADR003V01's own title, 'Decision-log entries separate human-reviewed judgment from tool-executed mechanics via a future adrpy log command') has no way to correct that through the tool today; ADR007V01's own H1 heading was hand-written as a workaround, with a note at the top of the file explaining the discrepancy. Two follow-ups tracked here: (1) evaluate whether `supersede` should gain an optional --title flag (mirroring how `new` already takes one), the same design-escalation discipline this session used for every other trade-off; (2) once that exists (or a decision is made not to add it), retitle ADR007V01 to its own real title instead of carrying ADR007V01's H1-heading workaround.

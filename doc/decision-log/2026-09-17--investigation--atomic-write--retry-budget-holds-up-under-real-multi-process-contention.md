# atomic_write_bytes's retry budget holds up under real multi-process contention, unlike an in-process-thread probe suggested

Round 8 resilience audit, Finding 3 (Low, explicitly self-caveated): a probe using 4 Python threads in ONE process (no yield between reads) measured 0 of a writer's attempts succeeding against `atomic_write_bytes`'s own 5-attempt exponential-backoff retry budget, contradicting the module's own docstring claim of empirically-tuned reliability. The reporting agent explicitly flagged this as "a harsher, tighter loop than 4 separate CLI processes would typically produce" and recommended re-measuring under real multi-process load before treating it as a confirmed field failure rate.

Investigated with a real reproduction: 1 writer process looping `atomic_write_text` + 4 separate reader processes looping `load_repo_config`, no pause, over 6 seconds (disposable script, not part of the repo). Result: the writer succeeded **852 of 854 attempts (99.77%)** -- only 2 exhausted the retry budget, a ~0.23% failure rate matching the ~0.2% rate already measured and accepted elsewhere in this codebase (core/lifecycle.py's own comment). The in-process-thread probe's "0 succeeded" result does not hold up under real multi-process conditions -- threads sharing one process's GIL and doing back-to-back reads with zero yield is a materially harsher scenario than genuinely separate OS processes.

No code change made -- the current retry budget (5 attempts, exponential backoff) is not shown to be insufficient under realistic contention. Not treated as `risk-accepted` either, since there is no unresolved risk on the table: the investigated hypothesis (the retry budget is measurably insufficient) did not hold.

Architectural review (Round 43): the result stands for readers outside adrpy (an editor, a sync client, an antivirus); concurrent adrpy processes on one working copy are no longer a supported pattern (ADR001). The budget is now per step: 5 attempts to prepare the temp file and 5 to commit it (`core/fs.py`).

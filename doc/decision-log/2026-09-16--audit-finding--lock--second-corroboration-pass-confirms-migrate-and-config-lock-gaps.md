# Second corroboration pass confirms and fixes migrate/config's missing lock; narrows the config fix

**Front:** Stability (round 4, second corroboration pass -- 2 independent instances) | **Severity:** High

ADR001's own "Negative Consequences" section flagged the `migrate`/`config`/`init` lock gaps as single-audit-instance findings needing a second, independent pass before being treated as confirmed. Two independent `audit-stability` instances were run against exactly that scope, given only the code and the general question ("is this command safe under concurrency"), not the original pass's own hypothesis or reasoning, so as not to bias a fresh look. Both independently reproduced real, empirical defects in `migrate` and `config` (2 of 2 agreement on every core finding).

**`migrate`** (HIGH, reproduced by both): held no lock at all. Worst reproduced scenario: a concurrent `migrate` re-reading a file's current bytes after a legitimate `approve` write (a command correctly following ADR001, its own `verify_still_held()` passing honestly) silently erased that write, burying it as opaque body content under a second, blank header -- defeating ADR001's own mutual-exclusion guarantee for a command that did everything right. Fixed: wrapped in the same `acquire_repo_lock` as the other 7 commands, with `verify_still_held()` checked before every per-candidate write, not just once.

**`config`** (HIGH, reproduced by both): read-merge-write of `adr-config.adrplus` with no lock at all. Two concurrent calls editing DIFFERENT fields -- whichever wrote last silently discarded the other's edit, violating this command's own documented contract ("an omitted flag preserves the repo's current value, never resets it"). First attempt used a cheaper mitigation (detect a concurrent change via a before/after text comparison, fail loudly instead of losing the update) specifically to avoid a perceived obstacle: the lock's scope would derive from `config.folderadr`, a field this same command can edit. On reflection that obstacle doesn't hold -- locking on the pre-edit `folderadr` (read before any write) is exactly what every concurrent caller agrees on until a write actually lands, the same way every other command already resolves its own lock directory once, up front. Fixed properly instead: brought under the same lock. Strictly better than the detect-and-fail mitigation it replaced -- the second caller no longer needs to fail, it waits, then reads fresh once it acquires the lock, so BOTH edits survive. Also closed a related gap the lock scope surfaced: `config` doesn't require the decisions folder to already exist (unlike the other 8 commands, which only ever run after `init` created it) -- `folder.mkdir(parents=True, exist_ok=True)` before locking, matching `init`'s own existing precedent for the identical situation.

**`init`** was also investigated in this same pass; its own findings and the resulting decision (stay exempted on its fresh-bootstrap path, accepted risk, with a visibility plan) are recorded directly in `doc/adr/ADR001V01-...md` itself, not here -- that is a durable architectural decision (what `init`'s scope under this ADR's own invariant is), not an audit finding about a defect that got fixed.

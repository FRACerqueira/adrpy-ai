# Title lacked filesystem-safety validation (NTFS ADS orphan via ':'); migrate's title skipped all validation

**Front:** Security audit (round 23, 2nd pass, new territory beyond round 22's marker fix) | **Severity:** High | **Resolution:** Direct | **Round:** 23

Round 23 (Security's 2nd pass, searching for new territory beyond round 22's marker-forgery fix) found and I independently live-reproduced two real defects, both closed. (1) HIGH-ish, closed as field-contains-forbidden-character: title is the only free-text field that lands inside an actual filename component (naming.build_filename), not just a header-table cell -- reject_embedded_delimiter's own blacklist ('|'/line-breaks) was never enough for it. ':' is uniquely dangerous: it is not an invalid Windows filename character, it is the NTFS Alternate-Data-Stream separator, so the temp-file WRITE succeeds (interpreted as a stream on a base file NTFS auto-creates) -- only the final rename to the real name fails, and the error-path cleanup only removes the named stream it just wrote, leaving that auto-created base file behind as a permanent, 0-byte, un-cleanable orphan (confirmed live, 3 repeated calls accumulate 3 separate orphans; cleanup_orphaned_temp_files only globs '*.tmp', which this leftover's name never matches, and it lacks '.md' too, so scan_decisions/explore never see it either -- silent, unbounded repository pollution). Worse: version/revise/supersede never validated title at all -- they re-read it from the target's own header cell or the predecessor's own filename, so this was reachable via a hand-edited or migrated file with no live --title flag ever attacker-controlled. Fixed with a new function, reject_filesystem_unsafe_title (core/security.py), rejecting the full Windows-reserved set (`<>:"/\|?*`) plus control characters -- this project declares itself OS-independent (pyproject.toml), and every one of these is a legal, unremarkable filename byte on a POSIX host, where build_filename's output is used exactly the same way. Wired into new/version/revise/supersede at the exact point each already validates or re-reads title, right before build_filename. Confirmed via live reproduction that the fix closes the orphan (0 files left in the decisions folder after rejection) and via mutation testing (removing each of the 5 integration points independently made the corresponding test fail for the predicted reason). (2) Medium, closed as field-contains-forbidden-character: migrate's own title -- sourced from the raw, untrusted legacy filename, sliced positionally by parse_legacy_filename with zero character filtering -- skipped validation entirely, the only title-bearing field in the codebase with no check at all. Not end-to-end reproducible on this Windows box (every forbidden character already fails to exist as a real Windows filename, confirmed live), but real on a POSIX host where '|'/a line-break are legal filename bytes, reaching the exact same header-forgery class round 22's marker-forgery fix closed for status labels. Fixed by validating title the same way as every other command, with migrate's own per-file failure semantics preserved (CommandError added alongside OSError/UnicodeError in the per-candidate except clause, so one hostile legacy filename fails only that file, not the whole batch) -- proven via a monkeypatched parse result (mutation-confirmed: red when the check is removed). Both fixes' describe() text and .md mirrors updated. Two other checked vectors, confirmed clean but not fixed (no action needed): no subprocess/shell/eval anywhere in src/adrpy (confirmed via grep); path traversal via title remains independently blocked by resolve_within as a second line of defense (3 pre-existing tests, previously asserting path-outside-repository, now correctly assert the earlier, more specific field-contains-forbidden-character instead). One adjacent gap flagged but NOT fixed (out of this round's scope): revise.py's own scope/domain, re-read from the target's header cell, are never passed through reject_embedded_delimiter at all (unlike version.py's equivalent fields) -- same shape as this round's own title findings, worth a follow-up pass.

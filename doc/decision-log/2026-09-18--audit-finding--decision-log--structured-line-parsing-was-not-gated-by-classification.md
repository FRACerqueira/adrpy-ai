# Structured-line parsing wasn't gated by the entry's own classification

**Front:** Stability audit | **Severity:** Medium | **Resolution:** Direct | **Round:** 12

_parse_entry attempted the Front/Severity/Round regex match, and separately the Reopen-when match, against every entry's first few lines unconditionally, regardless of the classification already known from its own filename. Two concrete failure modes confirmed: a non-structured entry (e.g. scope-note) whose free-form body happens to open with prose shaped like '**Front:** ... | **Severity:** ...' gets silently misread as a real structured line, skewing next_round's own count upward with no real audit-finding/doc-drift entry backing it. Separately, a hand-written/legacy structured entry with a non-integer Round (this project's own tooling explicitly anticipates hand-written entries) has its ValueError caught and silently skipped by the existing guard -- but because the match itself isn't classification-gated, that guard could already be reached from the wrong context, masking the same class of issue. Fixed by gating both regex attempts on the classification parsed from the entry's own filename: the Front/Severity/Resolution/Round match only runs when classification is audit-finding/doc-drift, and the Reopen-when match only when it's deferred -- matching exactly what build_entry_content itself already writes for each classification, so parsing and writing are symmetric.

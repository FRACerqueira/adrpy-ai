# reject's two-write order reversed: the predecessor is now reverted BEFORE this decision's own status write

Retracts the write order the 2026-09-18 decision-log entry (reject-partial-success-data-and-init-scan-incomplete-doc-fixed) built its error-reporting improvements on top of. Round 35's core resilience front found that order (this decision's own status first, the predecessor's revert second) could leave a predecessor permanently, unrecoverably stuck: every lifecycle command's shared eligibility check (core/lifecycle.py's _ineligibility_reason_for_proposed_state) treats status_change='Superseded' as a universal terminal state before any command-specific check even runs, and there is no 'unsupersede' verb anywhere in the 14-verb CLI -- so a persistent failure on the second write (disk full, a killed process) between commits left the predecessor Superseded-by a file that was actually Rejected, untouchable by approve/reject/undo/supersede/version/revise forever. Reproduced end to end: approve -> supersede -> reject with the predecessor's own write failing. The 2026-09-18 entry's own goal (never leave a partial mutation unreported) still holds and is preserved -- it's just applied to the new order's own remaining partial-success case (this decision's own write failing AFTER the predecessor was already reverted for real) instead of the old order's case. Fixed in cli/reject.py: the predecessor is reverted first; every failure up to and including that write now leaves nothing committed at all, safely retryable from scratch. A new failure code (reject-own-write-failed-after-predecessor-reverted) covers the one remaining genuine partial success, naming the already-reverted file via data.predecessor_file. Retrying reject after that specific failure is safe and completes automatically for a predecessor with no version/revision history (the common case) -- the predecessor lookup recognizes a single-member family whose one member is no longer Superseded as already-reverted. A predecessor with version/revision siblings can't be disambiguated this way once its own back-reference is gone (which sibling was the reverted one isn't derivable from file content alone) and still fails loudly on retry -- a disclosed, narrow residual, not silently papered over. 5 existing tests updated to the new semantics, 4 new tests added (predecessor-write-fails-first-with-no-write-made, safe single-member retry, deliberately-still-loud multi-member retry).

Architectural review (Round 43): the order stands: the predecessor is reverted first. The retry behavior described here does not: `reject-own-write-failed-after-predecessor-reverted` and the already-reverted lookup were removed. A failure on the second commit reports `multi-file-write-partially-applied` with data.applied, data.pending and data.repair, and the repository is refused until the row in data.repair is written by hand.

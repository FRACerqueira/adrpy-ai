# Title/separator collision, headertablevalues is_migrated forgery, and colon in statussup all closed

**Front:** Security audit (round 27, 6th pass -- systematic review, part A: core parsing/validation) | **Severity:** High | **Resolution:** Escalated | **Round:** 27

Round 27 (Security's 6th pass, a systematic method-by-method review of core/header.py, naming.py, casing.py, config.py, security.py, args.py -- requested explicitly by the project owner after 5 consecutive opportunistic rounds each found something) closed 3 findings, all live-reproduced. (1) HIGH: naming.build_filename joins the case-transformed title with config.separator without checking for a collision against the CONFIGURED separator value specifically -- with separator='.', a title starting with or consisting of an isolated '.' (e.g. '.x', '.gitignore') survives to_case almost verbatim under all 4 casetransforms (the word-splitter only consumes whitespace/'_'/'-', never '.'), producing a filename like 'ADR001V01..x.md' that parse_filename's own double-separator supersede-suffix split misreads, permanently orphaning the file with its sequence number silently reallocated -- the third distinct collision shape found this session (after an all-separator title and an empty title, each separately fixed earlier). The project owner was asked whether this specific pattern (recurring collision shapes) warranted a structural fix instead of a fourth narrow blacklist, and where such a fix should live: chose a round-trip verification inside naming.build_filename itself (re-parses its own output, refuses to return a filename that doesn't round-trip back to the exact number/version/revision/superseded identity just encoded), explicitly accepting that this gives core/naming.py the ability to raise CommandError for the first time -- a deliberate departure from that module's previous 'pure, never raises' convention, chosen over the alternative (a fifth narrow guard in core/security.py, called explicitly by all 5 title-producing call sites) specifically so every caller, present and future, is protected automatically. New failure code title-produces-unrecognizable-filename. (2) HIGH: headertablefields/headertablevalues were validated only for '|'/line-breaks, never for the marker-forgery characters the 4 status-label fields already get -- parse_header's own is_migrated detection is pure substring matching for an HTML-comment-shaped tail on the row these two fields build, so a hostile config setting headertablevalues to '<!-- x -->'-shaped text made is_migrated=True on the header of EVERY ordinary, non-migrated file ever written under that config (confirmed live), feeding counts_as_family_member and several lifecycle eligibility exceptions. Fixed with a new, narrower function (reject_marker_comment_syntax, blocking only '<!--'/'-->' -- NOT '('/')', which aren't part of this specific detection's own grammar and remain legitimately usable in these two fields) -- this one fixed directly, no design ambiguity. (3) MEDIUM: the Superseded row's successor-reference parsing (`superseded_text.find(':')`, core/header.py) finds the FIRST colon anywhere in the cell, not necessarily the real one the tool writes after the marker -- a statussup label containing its own ':' (e.g. 'Status: Superseded') corrupted superseded_by_file into the whole cell remainder, confirmed live to make `reject` fail with superseded-predecessor-not-found on a successor whose own primary write had already committed. Fixed directly by adding ':' to reject_status_marker_forgery_characters' existing blacklist for the 4 status-label fields. describe()/.md mirrors updated for all three. All three mutation-confirmed.

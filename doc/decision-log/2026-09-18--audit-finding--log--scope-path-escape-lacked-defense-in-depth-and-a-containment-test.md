# --scope path escape lacked defense-in-depth and an end-to-end containment test

**Front:** Test-Adequacy audit | **Severity:** High | **Resolution:** Direct | **Round:** 13

Not a currently-exploitable bug -- validate_scope's own kebab-case regex already rejects '/' and '\' outright, so no crafted --scope escapes the decision-log directory today. The finding is that nothing in the test suite proves WHERE the written file actually lands; every scope test only asserts the log-scope-invalid error code for known-bad inputs. Confirmed by simulating a future regression (weakening validate_scope to accept anything but '|'/empty, e.g. someone 'simplifying' it to reuse reject_embedded_delimiter without realizing scope is structurally different from front/summary): with that weakening applied, log.run returned success and wrote a file outside doc/decision-log/ entirely, in the parent doc/ directory, with attacker-controlled body content -- the exact vulnerability class round 12's own fix claimed to close, silently reopened, with the full suite still green. Fixed with a second, independent layer of defense: file_path now goes through resolve_within(log_dir, filename), the same real-path-resolution guard new.py's own file_path already used and log.py's first implementation never adopted. Confirmed via a test that monkeypatches validate_scope to a no-op and shows a 3-level '../' traversal is still caught (path-outside-repository), with no file written anywhere.

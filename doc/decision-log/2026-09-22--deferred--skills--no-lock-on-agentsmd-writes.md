# adrpy-skills does not extend ADR001V01's repository lock to its own write surface

**Reopen-when:** a programmatic (non-CLI) caller of adrpy.skills.installer emerges, or a slow-filesystem (network share/Dropbox) usage pattern is reported

The Round 33 stability front reproduced a real read-modify-write race on AGENTS.md between two concurrent adrpy-skills invocations, but only under an artificially injected delay between the read and the write (20/20 reproduced that way). Across 72 staggered launches of the real CLI as separate processes (0 to 0.4s apart -- the realistic pattern for two humans or agents invoking the command close together), 0 reproduced any corruption: the real read-to-write window in this tool is too short for two genuinely concurrent real invocations to collide in it without artificial help. adrpy-skills is a one-off installer invocation, not a long-running service with natural concurrent access, so extending ADR001V01's repository-wide lock (scoped today to the decisions directory) to cover adrpy-skills' own write surface (.claude/, .cursor/, .github/, AGENTS.md, doc/ai-skills/, ~/.claude/) was evaluated and declined for now -- it would be a real architectural extension with no matching measured risk at this tool's actual usage pattern. The unrelated torn-write/TOCTOU risks in the same area (see the other Round 33 entries in this scope) were fixed regardless of concurrency, since those apply even to a single invocation interrupted mid-write. Documented as a known limitation in doc/skills/README.md's own new 'Known limitation' section.

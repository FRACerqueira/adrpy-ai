# AGENTS.md block matching rewritten as a linear tag scan, closing an over-deletion bug and a quadratic DoS

**Front:** Round 34: re-verification front + Security front (independently, 2 fronts, same root cause and fix) | **Severity:** High | **Resolution:** Direct | **Round:** 34

Two independent Round 34 fronts (re-verification of Round 33's own fixes, and a first-ever security pass on adrpy-skills) found real bugs sharing one root cause: the per-skill DOTALL regexes (_agentsmd_block_pattern/_agentsmd_inner_pattern/_agentsmd_force_strip_all) used to locate a marked block. Re-verification found that _agentsmd_force_strip_all's greedy start-to-end (or start-to-EOF, when no end existed) spans deleted unrelated content sitting after or between a malformed block -- another skill's own valid block, or the user's own hand-written AGENTS.md content -- whenever --force cleaned up a truncated or duplicated block; reproduced concretely with two scenarios (a truncated block ahead of a clean decision-log block plus trailing hand-written notes; a duplicated block with a clean decision-log block interleaved between the two copies) via the real installer.install(force=True) path. Security independently measured the same regex family's O(n^2) cost against adversarial content with many :start tags and no matching :end anywhere -- ~9.5s at 771KB, reachable even via the read-only list command (default --provider all includes agentsmd). Fixed by replacing the whole family of per-skill DOTALL block/inner patterns with a single linear scan matching one tag line at a time (_agentsmd_all_tags, no .*/DOTALL at all, so no catastrophic backtracking is possible), then pairing each skill's own start/end tags in Python by exact position. Every remove/replace/force-strip operation now works off those exact positions instead of a regex span that could overshoot, closing both bug shapes (truncated and duplicated) and the DoS at once, since all three came from the same underlying 'can't precisely bound one skill's own block without backtracking-prone scanning' defect. 3 new red/green tests: 2 reproduce the over-deletion scenarios (confirmed failing against the pre-fix code -- the unrelated content was actually deleted), 1 times list_installed against 3000 unmatched tags (confirmed 8.69s against the pre-fix code, well under 1s after).

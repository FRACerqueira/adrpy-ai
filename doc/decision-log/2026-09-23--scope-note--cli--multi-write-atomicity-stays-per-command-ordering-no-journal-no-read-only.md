# Multi-write atomicity stays per-command write ordering; an intent journal and read-only family marking were evaluated and declined

Round 38 found several ways a multi-write command (supersede, reject) could still leave a wrong or wrongly resumed state, and raised whether a structural mechanism should replace per-command write ordering. Three options were evaluated. (1) Mark the whole family read-only while a state change runs, then restore it: declined. A read-only file mode does not stop os.replace or unlink on POSIX (those depend on the directory's permissions), and on Windows it blocks this tool's own os.replace. Marking N files is itself a multi-write that can fail partway. After a kill nothing restores it, and it carries no owner or timestamp to tell in-progress from stale, unlike core/lock.py's lease (ADR001V01). It breaks the user's editor and git checkout on Windows. It cannot tell the tool's read-only from a user's own. It would not stop the supersede number-reuse bug, since new creates a file outside the family. And working fully in memory contradicts ADR006V01's streaming. (2) An intent journal (write-ahead record under the existing repository lock, rolled forward by the next command): declined by the project owner as a new cross-cutting mechanism. (3) Keep per-command write ordering: chosen. The artifact that claims a number or is recoverable is written first, and each remaining case is fixed individually, following 2026-09-22--retraction--cli--reject-write-order-reverted-predecessor-first.md and 2026-09-23--audit-finding--cli--supersede-writes-successor-first-and-resumes-on-retry.md. A cheap preflight for persistent conditions (target folder not writable, read-only volume) stays available as a separate, optional improvement; it cannot catch transient failures such as a sharing violation, a full disk mid-write, a kill or a lost lock.

Architectural review (Round 43): part of this is superseded. Per-command write ordering stays and no intent journal was added, but the review added a prepare-then-commit step for multi-file writes (`core/fs.prepare_write`/`commit_write`): every file is written to its temp first, then committed in a fixed order, so a persistent condition fails before anything is committed. The individually fixed recovery cases were replaced by one code, `multi-file-write-partially-applied`, with data.repair for a manual repair, and there is no resume. The lease and the lost lock named here no longer exist (ADR001).

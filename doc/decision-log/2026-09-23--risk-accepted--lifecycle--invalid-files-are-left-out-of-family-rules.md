# a decision file whose header does not parse is left out of every family rule, visibly

The owner's rule, implemented in b4d6d4c and documented in doc/lifecycle.md: the filename decides identity and numbering, counting every file; the header decides status, counting only headers that parse. A file whose header does not parse -- damaged by hand, broken by invalid bytes, or never given one -- is left out of the family rules instead of failing the command. Accepted: a family made inconsistent by an edit outside the tool (two live decisions after a hand-broken Superseded cell) is not prevented. Visibility: every command that left a file out says so in warnings ('<file>: ignored -- its header does not parse (<reason>); see explore.'), explore shows header.state and header.invalid_reason, and an invalid target's detail names the reason. Where it still refuses: reject when any file of the predecessor's family does not parse, supersede when a file pointing back does not, version/revise when the number they would create is already held, migrate when a damaged tool header exists, and every OS error (unreadable file or folder). A lossy decode only matters when it breaks the header. Residual: a legacy file whose first 12 lines hold an exact |--|--| table row reads as a damaged tool header and blocks migrate, with a detail naming it.

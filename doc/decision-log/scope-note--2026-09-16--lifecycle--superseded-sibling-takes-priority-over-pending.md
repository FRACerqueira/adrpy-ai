# Superseded sibling takes priority over pending sibling in undo/version/revise

`undo`/`version`/`revise` have consistently checked `has_superseded_sibling` before `has_pending_sibling` since before round 4, but no test ever constructed a family with both conditions true at once, and no prior record stated whether this order was deliberate. Round 5's test-adequacy re-run (Finding 1) surfaced the gap; investigated first against `C:\Sources\AdrPlus\README.md` (the real tool's own eligibility table only states "not superseded" as a flat gate for `version`/`revise`/`undo`, identically for all three, and never distinguishes a priority between a superseded and a pending sibling -- this granularity, and therefore this ordering, is original to adrpy-ai, with no external reference to diverge from).

**Confirmed with the user:** superseded must win, deliberately -- it means the whole family was already replaced, which blocks it regardless of any other sibling's own state. This was an existing (undocumented) decision's boundary being made explicit, not a new one. Now pinned by a dedicated test in each of the three commands' own test files (`test_status_transitions.py`, `test_version.py`, `test_revise.py`), each verified non-vacuous by temporarily swapping the order and confirming the test then fails for the right reason.

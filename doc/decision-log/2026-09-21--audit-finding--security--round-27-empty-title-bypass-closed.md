# Empty title bypassed the no-case-transform-content guard, permanently orphaning a migrate-then-supersede successor

**Front:** Security audit (round 27, 6th pass -- systematic review, part C: CLI command layer) | **Severity:** High | **Resolution:** Direct | **Round:** 27

Round 27 (Security's 6th pass, systematic review of all 14 CLI commands, __main__.py, and help.py) closed one HIGH finding: reject_title_with_no_case_transform_content's own `if value and ...` guard never checked a literal empty string -- to_case('') degenerates the exact same way a whitespace/'_'/'-'-only title does (the round-24 finding this function exists to close), but the empty-string case slipped through unrejected. Empty title is reachable only through migrate: naming.parse_legacy_filename can genuinely return '' for a legacy filename with no title segment (e.g. '0001.md' under migrationpattern='N00:04T04'), and migrate's own three title guards -- reject_embedded_delimiter, reject_filesystem_unsafe_title, and this one -- all silently accepted it, writing a migrated header with a permanently blank title cell. Confirmed live end-to-end: migrating such a file, then calling `supersede` on it, produced 'ADR002V01---001.md' -- unrecognized by either naming scheme, permanently -- with `supersede` reporting total success and `warnings: []`. The predecessor's own write had already committed Superseded; there is no CLI recovery path for the orphaned successor. Also confirmed the contamination propagates through version/revise even without supersede involved (a blank-titled file still gets a recognizable filename from those two specifically, but perpetuates the blank title for a later supersede to orphan). Fixed by removing the `value and` exemption -- title is never an optional/sentinel field anywhere this function is called (unlike domain/scope, which legitimately use '' as 'not provided' elsewhere in this codebase). Also now caught independently and earlier by round 27's own Part A fix (naming.build_filename's new round-trip verification) -- defense in depth, not redundant: the security.py fix rejects at the SAME validation point as every other title check (consistent error UX, an agent gets the same kind of error regardless of which specific title problem triggered it), while the naming.py fix is the structural backstop that would have caught this even without this specific patch. Mutation-confirmed. Also re-verified (not just trusted): every family-membership guard (has_superseded_sibling/has_pending_sibling) across approve/reject/undo/supersede correctly passes exclude_from_encoding_check=path; reject.py's second-phase predecessor-family scan correctly omits it (different family number, no exclusion needed); every command's own title/scope/domain validation runs before use, including fallback-to-latest-member values.

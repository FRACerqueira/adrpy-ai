# the header's "Values" column label only says "Migrated" on an actually-migrated file, unlike the real tool's literal label on every file

`core/header.build_header`'s row-2 column label (`"Adr-Plus Fields" | "Values" [+ " Migrated"]`) now includes the word "Migrated" only when `migrated=True` is passed — true only for files stamped by the `migrate` command. Every other command (`new`, `version`, `revise`, `supersede`, and the header-preserving rewrite path in `core/lifecycle.py` for `approve`/`reject`/`undo`) now produces a label that reads just `"Values"` for a file that was never migrated.

**Why this diverges, and why it's safe to:** captured byte-for-byte against a real `adrplus new` run (AdrPlus 1.0.0, Windows; `tests/test_header.py`'s own fixture-parity test), the real tool's row 2 literally reads `"Values Migrated "` on every file it creates, migrated or not — only the trailing `<!-- Migrated -->` HTML comment is conditional. This is the real tool's own static resource string, not a computed value; it was raised as a usability concern (the word "Migrated" on a freshly-created, never-migrated file reads as a claim that migration happened). Confirmed safe to diverge: `parse_header` (`core/header.py:135-136`) detects `is_migrated` exclusively from the trailing `<!-- Migrated -->` HTML comment — the label text itself is never inspected on read, by adrpy-ai's own parser or (per the header's own docstring, mirroring `AdrService.ParseAdrHeaderAndContentAsync`) by the real tool's either. Removing the word where it doesn't apply changes zero parsing behavior on either side; it only removes a misleading word from a column that was never meant to carry per-file information. `migrate`'s own already-migrated output (`migrated=True`) is byte-for-byte unchanged. Escalated and confirmed with the user (commit introducing this file).

# supersede now writes the successor first and resumes onto it on retry, so a failed second write can no longer misattribute the predecessor

**Front:** Round 37: multi-write recoverability front (core) | **Severity:** High | **Resolution:** Escalated | **Round:** 37

The recoverability sweep (2026-09-22--investigation--cli--multi-write-recoverability-sweep-log-and-migrate-recoverable.md) found a failed successor write left the predecessor Superseded with no successor, calling it a softer gap than reject's. Reproducing it during round close showed it is worse: the predecessor recorded ': 002' with no ADR002 on disk, the next new took 002, so the predecessor silently and permanently claimed to be superseded by an unrelated decision; a retry only got already-superseded. The project owner chose between reversing the write order (same shape as 2026-09-22--retraction--cli--reject-write-order-reverted-predecessor-first.md), keeping the order with a resuming retry plus number reservation in the shared next_number, and a new --supersedes flag on new. Fixed in a1de43d with the first: the successor is written first, claiming its number on disk; its failure writes nothing (supersede-successor-write-failed), and a failure marking the predecessor afterward reports supersede-write-failed with data.successor. Re-running supersede resumes onto exactly one non-Rejected successor still Proposed, marking only the predecessor; one approved since, or more than one, is refused with the new supersede-orphaned-successor-not-resumable. The first version of the fix refused supersede, reject-the-successor, supersede-again, a normal flow that worked before (red with the fix, green with it stashed); caught by an adversarial positive control before commit, fixed by excluding Rejected successors. 6 red/green tests plus 3 controls; suite 1205 passed, 3 skipped.

# ADR004 guard/marker had five untested branches, all mutation-confirmed and closed

**Front:** Test-Adequacy audit | **Severity:** Medium | **Resolution:** Direct | **Round:** 19

A post-implementation adversarial test-adequacy pass on ADR004V01's marker/guard code found five uncovered branches, each confirmed via mutation (mutated, ran the suite, reverted). (1) The guard's field tuple was never tested for statusrej/statussup independently, in either call site (config or init --seed) -- shrinking the tuple to 3 fields left the full suite green. (2) existing_decisions was never asserted with more than one decision -- hardcoding it to 1 left the suite green. (3) marker_label_mismatches was only ever exercised on the Created row -- renaming the field names appended for the Changed/Superseded rows left the suite green, and no test independently proved the Superseded row's own marker resolves correctly under a changed config (every existing Superseded-row test read back under the SAME config it wrote, so the label fallback could have masked a broken marker path there). (4) A marker with different case (e.g. '<!-- accepted -->') silently fell back to label-text matching with zero signal -- fixed with re.IGNORECASE plus a lowercase-to-canonical lookup, since every downstream consumer requires the exact canonical case. (5) The precedence between this guard's own scan-incomplete code and init's pre-existing init-existing-numbers-scan-incomplete was confirmed by direct execution but never pinned by a test, and was not documented either. All five closed with new tests (mutation-verified) in tests/test_header.py, tests/test_config_command.py, and tests/test_init.py; case-insensitivity fixed in core/header.py; the scan-incomplete precedence is now also documented in config.py/init.py's own describe(). See doc/adr/ADR004V02-... for the case-insensitivity design decision.

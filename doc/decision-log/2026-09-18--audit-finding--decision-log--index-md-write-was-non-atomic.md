# INDEX.md's write was non-atomic, risking durable truncation on failure

**Front:** Stability audit | **Severity:** High | **Resolution:** Direct | **Round:** 12

regenerate_index wrote INDEX.md via a plain Path.write_text() call -- truncate-on-open, then write -- unlike every other writer in this codebase, which goes through core/atomic_write.py's atomic_write_text/atomic_write_bytes specifically to avoid a concurrent reader ever observing an empty or partially-written file. Confirmed empirically with a stress probe (roughly 800 entries to widen the write window, one thread calling regenerate_index repeatedly while another polled INDEX.md continuously): the file was observed at length 0 in 8 of 14681 reads. Beyond the transient tearing, a real OSError (ENOSPC, a permission failure) or the process dying at that exact instant would have left INDEX.md durably empty on disk, since write_text has no protection against a failure mid-write. Fixed by routing regenerate_index through atomic_write_bytes (not atomic_write_text, to preserve this function's own explicit LF-only convention regardless of host OS) -- a failed write now leaves the original file untouched, since atomic_write_bytes writes to a temp file and only replaces the real one via a single atomic os.replace at the very end.

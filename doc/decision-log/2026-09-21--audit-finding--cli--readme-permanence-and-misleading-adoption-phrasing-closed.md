# README lacked the permanence caveat; describe() overstated the adoption check's reach

**Front:** Usability audit (round 21, comprehensive unfiltered pass) | **Severity:** Medium | **Resolution:** Direct | **Round:** 21

A round-21 comprehensive usability pass, re-deriving ground truth from the actual code rather than comparing docs to each other, found two drifts. (1) README.md's Configuration section stated status labels/separator/migrationpattern are simply 'edited via adrpy config' with no mention that this becomes permanently impossible for most fields the moment the repository has a matching decision (doc/commands/config.md already documents this correctly; README's own top-level claim did not). Fixed by adding an explicit permanence sentence, pointing at ADR004V02 and adrpy help config. (2) config.py/init.py's describe() (and their .md mirrors) phrased the new adoption check as firing 'even when zero existing decisions are at risk' -- read as an implication that this coexists with a more common case where some decisions ARE also at risk. Re-derived from core/lifecycle.py directly: the adoption check is only ever reached after the blocking-fields check has already passed and NOT raised, so 'zero existing decisions at risk' is the only state the adoption check can ever run in -- the two outcomes are mutually exclusive by construction, not an edge case. Fixed the phrasing in both describe()s and their .md pages; added a new test pinning this precedence (test_config_blocking_fields_check_wins_over_the_adoption_check_when_both_could_apply), mutation-confirmed.

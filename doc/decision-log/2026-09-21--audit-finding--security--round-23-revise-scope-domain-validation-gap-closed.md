# revise.py never validated scope/domain re-read from the target header, unlike version.py's equivalent

**Front:** Security audit (round 23, follow-up investigation of a self-flagged gap) | **Severity:** Medium | **Resolution:** Direct | **Round:** 23

Round 23's own report flagged, but did not fix, an adjacent gap: revise.py never validated scope/domain (re-read from the target file's own header cells), unlike version.py, which re-validates them even when falling back to the latest family member's own current value. Investigated and confirmed live: a hand-edited '' (VT control character) in a decision's Scope cell survived an unrelated `revise` call unchanged, propagating into the new revision's own header and into `explore`'s own JSON output -- the exact data-hygiene defect reject_embedded_delimiter's own blacklist exists to prevent, just never wired up for this command's two fields. A literal '|' does NOT forge the table the same way: _extract_cell's own read-side parsing (core/header.py) already truncates a cell's value at the first '|', so it can never actually reach header.scope/header.domain as a raw character -- confirmed directly before ruling it out, not assumed. Fixed by adding reject_embedded_delimiter(header.scope, 'scope') and reject_embedded_delimiter(header.domain, 'domain') at the same point revise.py's own title validation already runs (round 22), mirroring version.py's precedent. Closed the class: checked supersede.py (already validates its own scope/domain unconditionally, whether from a flag or the header fallback) and new.py (scope/domain come only from flags, already validated) -- revise.py was the only gap. Mutation-confirmed (removing the two new calls made both parametrized tests fail with DID NOT RAISE).

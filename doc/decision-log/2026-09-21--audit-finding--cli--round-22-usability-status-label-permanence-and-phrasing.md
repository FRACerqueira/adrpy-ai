# Status-label permanence undocumented; README 'matching' phrasing wrong for separator; ADR self-contradicted its own revision count

**Front:** Usability audit (round 22, 4th pass, unfiltered) | **Severity:** Medium | **Resolution:** Direct | **Round:** 22

A round-22 usability pass (4th on this area) found three drifts, all independently reproduced against the code before fixing. (1) statusnew/statusacc/statusrej/statussup share the exact same permanent-block behavior as separator (both in _BLANKET_GUARD_FIELDS, core/lifecycle.py) but this was never stated user-facing -- the ADR, config.py/init.py's describe(), their .md mirrors, and README all only named separator/migrationpattern as permanent. Fixed by adding explicit status-label-permanence language to config.py/init.py's describe(), their .md mirrors, and README's Configuration section. (2) README's own phrasing ('become permanently fixed the moment the repository has its first matching decision') is wrong for separator, which is blanket (blocks on ANY decision, not just a matching one) -- 'matching' only correctly describes migrationpattern's legacy-scoped behavior. Fixed by splitting the sentence: status labels/separator block on any decision of any kind, migrationpattern blocks only once a legacy-scheme decision exists. (3) The ADR self-contradicted itself two bullets apart (one bullet said 'the fourth correction', the next, stale, unedited bullet said 'revised three times') -- fixed by merging into one bullet correctly saying four.

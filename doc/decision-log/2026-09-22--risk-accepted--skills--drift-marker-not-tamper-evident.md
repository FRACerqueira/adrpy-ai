# The content-hash drift marker is unkeyed by design -- documented as not tamper-evident, no HMAC added

Round 34's security front found the drift marker's hash algorithm and comparison are sound as a self-consistency check (full un-truncated SHA-256, string-equality, no weak-hash shortcut -- confirmed no way to force check_drift to return clean for mismatched content other than reproducing the real hash), but the algorithm is public and unkeyed: anyone with write access to a target file can compute their own valid-looking marker over arbitrary content. Checked concretely: install/remove never trust an existing clean file enough to skip regenerating content from the package's own bundled resources, so a forged marker grants no extra write/delete leverage there. The one real effect is on list (read-only, only hashes what's already present): a forged marker makes list report drifted: false for content that was never actually generated by this tool -- a false assurance signal for files that are literally AI-coding-agent instructions read and acted on by an agent. Evaluated adding a keyed signature (HMAC) and declined: this is a local, stateless CLI with no key-provisioning story, so an HMAC would need to invent key generation/storage/rotation infrastructure the tool has nothing like today, to close a risk that grants no write/delete leverage, only a misleading list read. Documented as a known limitation in doc/skills/README.md instead -- list's drifted: false should be read as 'matches its own recorded hash', not 'verified authentic'.

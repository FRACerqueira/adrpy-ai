# remove() no longer treats 'foreign' as safe to touch, closing a release-blocking gap

**Front:** Round 33: filesystem-security, hash-marker, and test-adequacy fronts (independently corroborated) | **Severity:** High | **Resolution:** Direct | **Round:** 33

install() already blocked writes on status in (drifted, foreign), but remove() only checked for drifted -- in 3 code paths: the generic per-file branch, the agentsmd marked-block branch, and the shared doc/ai-skills/<name>.md unlink (which had no drift check at all). A file/block with no adrpy-skills marker (foreign) was deleted unconditionally, success:true, no warning, even without --force. Reproduced concretely: 'adrpy-skills remove --provider claude --target global' with no other flags would delete a real, hand-authored ~/.claude/skills/<name>/SKILL.md predating any adrpy-skills install, since a hand-written file with no marker classifies as foreign. Fixed by extracting a shared _blocks_write(status, force) helper (status in (drifted, foreign, malformed) and not force) used identically by install() and remove() at all 6 write/delete sites, plus adding the missing drift check on the shared-doc unlink. A new TestRemoveForeignProtection test class (7 tests) reproduces the exact global-scope scenario and the shared-doc gap.

# Mutation testing found zero coverage on LockLostError handling, retry_warning, and index sort

**Front:** Test-Adequacy audit | **Severity:** High | **Resolution:** Direct | **Round:** 12

Three independent zero-coverage branches, each confirmed by mutating the production code and re-running the full suite unmodified. First: log.py's except (OSError, LockLostError) handler around index regeneration had a test only for the OSError branch -- removing LockLostError from the tuple entirely still passed all 42 tests at the time. This is the exact regression class this codebase already hit once for real, in supersede.py (tests/test_supersede.py's own test_supersede_reveals_predecessor_already_superseded_when_the_lock_is_lost_before_the_successor_write, whose own docstring states the handler used to bypass LockLostError entirely). Second: retry_warning()'s own 'succeeded only after N attempts' message was never exercised for this command -- commenting out the warnings.append(warning) block still passed all tests; every sibling write command already has this end-to-end test, log was the only one missing it. Third: regenerate_index's own entries.sort() call had zero coverage -- commenting it out still passed all tests, since no test populated the directory with entries out of natural order. Fixed by adding a dedicated test for each: the LockLostError branch (mirroring the existing OSError test), a retry-warning test (mirroring new.py's own), and a multi-entry out-of-order sort test asserting the resulting INDEX.md row order directly.

Architectural review (Round 43): the first of the three tests covered `LockLostError`, which no longer exists; it went with the lock (ADR001). The retry-warning and index-sort tests stand.

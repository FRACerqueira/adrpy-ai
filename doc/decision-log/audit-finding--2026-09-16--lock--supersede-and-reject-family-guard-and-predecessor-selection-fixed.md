# supersede now guards the whole family, and reject matches the actual predecessor instead of the latest sibling

**Front:** Stability (round 7), Findings 1 and 2 | **Severity:** High | **Resolution:** Direct

Round 7 stability audit, Finding 1: `supersede` had no family-wide guard at all -- unlike `version`/`revise`, which both check `has_superseded_sibling`/`has_pending_sibling` before writing. Two different members of the same family could each be independently superseded, producing two live successors and two Superseded predecessors: exactly the corruption shape ADR001's own Decision Drivers name as HIGH-severity reproduced corruption, and round 6's freshness fix does not close it (freshness only protects the same-file race, not a second, different family member). Reproduced deterministically, no race needed.

Finding 2, a follow-on: `reject` picked the predecessor to revert via `latest_in_family` (highest version/revision) instead of matching the family member whose own `superseded_by_file` actually names this successor. Reachable independently of Finding 1's bug -- any family with more than one member (e.g. from an earlier `version` bump) where the superseded member isn't the latest already selects the wrong file, un-superseding the untouched sibling and leaving the real predecessor permanently, silently Superseded, while reporting a false `undone_predecessor`.

**Fix**: `supersede` gained the same `has_superseded_sibling`/`has_pending_sibling` guard `version`/`revise` already use (`family-member-superseded`/`family-member-pending`, no write made). `reject` now matches the predecessor by its actual back-reference (`superseded_by_file`, a bare zero-padded sequence number per `mark_superseded`'s own docstring, never a filename) instead of "latest in family". An existing test's fixture data (`superseded_by_file="ADR002V01-successor--001.md"`) was itself inaccurate against this real format -- corrected alongside the fix, since the old code never actually read that field.

# explore read and decoded a candidate's entire file content instead of just the header, an unbounded memory-exhaustion DoS

**Front:** Security audit (round 26, 5th pass, new territory beyond rounds 22-25) | **Severity:** High | **Resolution:** Direct | **Round:** 26

Round 26 (Security's 5th pass) found and I independently live-reproduced a HIGH severity defect: explore's _build_entry (cli/explore.py) read and decoded a candidate's ENTIRE file content (path.read_bytes()) for every scanned file, even though parse_header only ever consumes the first 12 lines -- architecturally inconsistent with every other bulk scan in this codebase (family_members, migrate's scan phase), which deliberately use a bounded header-only read for exactly this reason. This matters specifically because explore is read-only and the natural 'safe first look' an AI agent would run against an unfamiliar or external repository, with no size warning before a matching file is read. Confirmed live: a 100MB body file drove peak traced memory to ~500MB (5x amplification: raw bytes + decoded str + split-lines list held concurrently) for a single candidate, versus ~32KB for the bounded header read; nothing in the code caps file size, so this scales to a multi-GB memory-exhaustion DoS against any process running explore against a hostile/external repo. Fixed by switching to read_header_lines_with_report (core/lifecycle.py), the same bounded, retry-tolerant, lossy-decode-reporting read every other scan already uses -- same PermissionError-retry and encoding_repaired semantics preserved. Confirmed live post-fix: the same 100MB file now peaks at ~32KB instead of ~500MB. Mutation-confirmed with two independent mutations (an oversized _HEADER_READ_CHUNK_SIZE to prove the test's own guard fires on a real oversized read through the correct I/O path, and a reversion to path.read_bytes() to prove the test catches the actual historical vulnerability) -- the first mutation attempt (a read-size-limiting wrapper around builtins.open) was itself found to be a vacuous guard, since Path.read_bytes()/Path.open() call io.open() directly and never route through builtins.open, so it silently failed to intercept the very regression it was meant to catch; replaced with the same direct Path.read_bytes/read_text patch already proven correct by read_header_lines' own sibling test in test_lifecycle.py. Two pre-existing tests (best-effort/retry-on-PermissionError) also needed their own monkeypatch target moved from Path.read_bytes to builtins.open, since the new implementation's I/O primitive changed. Seven other vectors checked and closed as safe, no action needed: atomic_write.py's temp-file naming (128 bits of UUID randomness, unguessable before the write, no TOCTOU symlink race feasible); --seed <path> traversal (by design, not restricted to any base directory -- same local-filesystem-read privilege the invoking process already has either way; confirmed no file content leaks via any error message); deep non-symlink directory nesting as a distinct resource-exhaustion vector (live-tested a real 5,000-9,700-level-deep tree, no crash, no amplification -- unlike the already-closed symlink-loop case, construction cost for a real tree is the same order as traversal cost, no attacker asymmetry); parse_flags/core/args.py flag-value smuggling (live-tested dash-prefixed and flag-shaped values as literal values, no bleed-through, no injection); activeplugins/disableplugins config fields (confirmed via grep to be purely inert metadata with no runtime reader anywhere); environment variable trust (only APPDATA/XDG_CONFIG_HOME for the OS user's own per-user config directory, standard convention, not attacker-influenced data under this project's own threat model); concurrency races beyond the lock file itself (re-read approve.py/supersede.py in full -- verify_folderadr_unchanged_since_lock, fresh read_target, fresh strict family_members, and lock.verify_still_held() immediately before every write, with no stale pre-lock state ever used for a write decision); cross-platform separator confusion (title's own filesystem-unsafe blacklist already rejects both '/' and '\', and folderadr's _is_relative_path plus resolve_within's real path resolution already cover every Windows/POSIX/UNC absolute-path form).

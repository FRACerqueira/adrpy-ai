# approve/reject/undo now re-validate title/scope/domain read back from the header, matching the other 4 per-file writers

**Front:** Security audit (round 28, 7th pass -- systematic review split by invariant, invariant B: every free-text field validated consistently on every consumption) | **Severity:** Low | **Resolution:** Direct | **Round:** 28

Round 28's field-validation-invariant pass found that approve.py/reject.py/undo.py were the only 3 per-file writers (of 7 total) that never re-ran reject_embedded_delimiter/reject_filesystem_unsafe_title/reject_title_with_no_case_transform_content on the title/scope/domain they read back from the target's own header before reusing them -- version.py/revise.py/supersede.py/migrate.py all already do this. Confirmed live (a hand-crafted hostile scope/domain value, e.g. 'A(B)C:D<!--E-->F', round-tripped through a real approve call with no rejection and no corruption) that this was currently inert, not exploitable: _extract_cell structurally truncates an embedded pipe before it can survive parsing, and these 3 commands never call build_filename (no rename), so the filesystem-unsafe/no-case-transform risks -- which only matter for a rename -- never materialize either. Fixed for consistency/defense-in-depth anyway: the gap is real for any future change to these 3 commands (a rename, or a change to _extract_cell's own truncation behavior) that would silently reopen it with no test currently guarding it.

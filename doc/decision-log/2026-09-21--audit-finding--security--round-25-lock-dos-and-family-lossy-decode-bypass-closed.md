# Lock timestamp overflow caused a permanent repository DoS; a corrupted sibling was silently invisible to the two-live-successors guard

**Front:** Security audit (round 25, 4th pass, closing 3 carry-over items from round 24) | **Severity:** High | **Resolution:** Direct | **Round:** 25

Round 25 (Security's 4th pass) closed the three items round 24 had explicitly flagged as not fully checked. Two were real defects, both live-reproduced and fixed; one was closed safe with evidence. (1) Medium, fixed: core/lock.py's _read_lock parsed the lock file's timestamp with bare float(), which silently overflows to inf for a several-hundred-digit numeric string -- not a ValueError, so the existing except clause never caught it. _reclaim_if_abandoned's own check (time.time() - timestamp <= abandon_after) becomes -inf <= abandon_after, which is ALWAYS True for any abandon_after including 0 -- the lock could never be judged abandoned again, a permanent, repository-wide denial of service (every write command times out indefinitely, unlike the documented 30s stale-lock reclaim for an ordinary crash). Requires local write access to the decisions folder already (e.g. a lock file synced/restored from elsewhere with a garbage timestamp). Fixed with a math.isfinite() check, treating a non-finite timestamp the same as an unparseable one (falls back to the file's own mtime, which still advances toward reclaim over real time). (2) High, fixed: family_members (core/lifecycle.py) used the no-report header read, so a sibling with invalid UTF-8 bytes in its header (e.g. corrupted or hostile-migrated) silently failed to parse and was EXCLUDED from the family with zero signal -- not merely unwarned about, but invisible to has_superseded_sibling/has_pending_sibling, the exact guard every per-file command relies on to prevent two live successors (ADR001's own concern). Reproduced live end-to-end: a genuinely Superseded V01 with 2 corrupted bytes in its status row let `version` on its sibling V02 succeed and create a duplicate V03, with warnings:[]. Fixed by switching to the with-report read and failing closed (new code family-scan-unreliable-encoding, data.unreliable_files, mirroring migrate's own migration-scan-unreliable-encoding for the identical hazard) whenever a REPLACEMENT CHARACTER actually lands within the parsed header lines specifically -- not merely anywhere in the bounded read's byte-chunk, which commonly covers a small file's entire body too and would otherwise false-positive on already-tolerated body-only corruption (9 existing tests initially broke on this distinction before it was narrowed correctly). A second parameter, exclude_from_encoding_check, exempts the one file every real caller is already reading via read_target from this new check -- that file's own encoding reliability is separately surfaced as a warning there, and the command's write is expected to heal it, the same already-established tolerance every read_target caller relies on; wired into all 6 call sites (approve/reject/revise/supersede/undo/version). Both directions mutation-confirmed. (3) Closed safe, evidenced: help/describe() under a tampered config -- _defaults_preview() does pull live config values into its JSON output, but json.dumps unconditionally escapes quotes/backslashes/control characters (a hard JSON-spec requirement), and a corrupted install-level config fails closed through __main__.main's own catch-all into a clean {success:false} envelope; confirmed live with a hostile folderadr value containing an embedded newline and quote, round-tripped through json.loads unchanged, no structural corruption, no multi-line output.

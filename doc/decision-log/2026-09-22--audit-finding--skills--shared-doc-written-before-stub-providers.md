# Shared doc is now written before any stub-mode provider that references it, closing a dangling-reference window

**Front:** Round 35: resilience front | **Severity:** Medium | **Resolution:** Direct | **Round:** 35

Round 35's resilience front found needs_shared_doc was only known as a side effect of the provider loop, and the shared doc (doc/ai-skills/<name>.md) was written only after the whole loop finished, even though it's derivable up front from the requested providers alone with no I/O. Reproduced: interrupting install(providers=['copilot','agentsmd'], skills=['decision-log']) between the two stub-mode providers left the first one's file (copilot's own stub) referencing a shared doc that was never written. list_installed() could not detect this -- it only checks the stub's own hash marker, never whether the shared doc it references actually exists, so it reported a false installed:true, drifted:false for the whole window. The corruption self-heals on the next uninterrupted install() (the stub's status was still clean, not foreign/drifted, so nothing blocked the rewrite) and remove() already handles the dangling state correctly (its own shared_path.exists() guard silently no-ops). Fixed by computing needs_shared_doc from provider_names/PROVIDERS up front and writing the shared doc before the provider loop starts, so a stub file can never be written before the shared doc it needs exists. New red/green test confirmed failing against the pre-fix code (a stub write observed the shared doc as not-yet-existing). Residual, not fixed here: list_installed() still cannot detect a shared doc that goes missing by some OTHER means later (e.g. a user manually deleting doc/ai-skills/<name>.md while leaving stub files in place) -- narrower than this fix's own scope, not raised as a separate finding, noted here for visibility.

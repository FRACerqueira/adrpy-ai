# Round 32: closed 2 over-claims and 1 under-claim in ADR008V01s new failure_codes field

**Front:** Test-Adequacy (independent verification of ADR008V01s own implementation) | **Severity:** Medium | **Resolution:** Direct | **Round:** 32

An independent, adversarial verification pass (requested by the repo owner before implementation even began, specifically because 137 hand-written code-to-condition mappings across 14 commands is exactly the kind of repetitive, error-prone transcription work prior rounds have found real bugs in) found 3 confirmed defects in ADR008V01s own failure_codes field, re-verified against the real source before fixing:

1. Over-claim: field-is-blank was listed by approve/reject/undo/revise (via core/lifecycle.pys own SHARED_FAILURE_CODES, incorrectly treated as universal to all 6 per-file commands) even though none of them can structurally reach it -- each only calls reject_embedded_delimiter on header.title/scope/domain, which core/header.pys own _extract_cell always .strip()s before returning; reject_embedded_delimiters own blank check (value != "" and not value.strip()) can never be true on an already-stripped value. Only supersede/version genuinely reach it, via a raw --scope/--domain flag value used before any header fallback. Fixed by moving field-is-blank out of the shared dict and into supersede/version own inline dicts.

2. Over-claim: same root defect, independently, in migrate.py -- title = (parsed.title or "").strip() runs immediately before reject_embedded_delimiter(title, ...), so the code was listed but structurally unreachable there too. This is notable as a recurrence of the identical invariant violation (validate raw, not pre-stripped, values) through a different mechanism (explicit .strip() vs. upstream pre-stripped extraction) than the first occurrence -- confirms this is a real class, not a single typo.

3. Under-claim: io-error was missing from installconfig.py, the one write-performing command whose 3 atomic_write_text call sites are never wrapped in attach_warnings (or any other OSError-catching mechanism) -- a raw OSError (e.g. a PermissionError exhausting the retry budget) genuinely propagates uncaught to __main__.pys generic handler, which reports it as io-error, exactly as already documented for every other writer.

Also corrected, lower severity: core/config.pys own condition text for config-field-contains-forbidden-character omitted that headertablefields/headertablevalues additionally reject <!--/--> via reject_marker_comment_syntax (a real but separately-scoped check from the 4 status labels own (/)/<!--/-->/: rejection already documented).

No other over-claims, under-claims, or condition-text inaccuracies were found: the verification pass independently re-derived every commands own reachable-code set from its real call graph (not reusing the construction-time mapping) and spot-checked ~20 condition-text entries against real raise sites. Full-registry coverage (all 137 codes appear in at least one commands failure_codes) and no-duplicate-per-command structural tests both re-verified as passing for real, not weakened. 2 new permanent regression tests pin the corrected boundary (field-is-blank claimed only by supersede/version, not the other 4; installconfig documents io-error) so a future re-introduction of either defect is caught mechanically.

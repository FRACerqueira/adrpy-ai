# Every write regenerates an index of the decisions in the decisions folder

## Deciders

* Deciders: Fernando Cerqueira (repo owner), decided while planning the repository config and naming changes (2026-09-29).

Technical Story: a repository's decisions can only be listed by running `adrpy explore` or by reading the folder's file names; nothing in the repository itself gives a reader, on GitHub or in an editor, one page with every decision, its title and its state. The decision log already has such a page, its `INDEX.md`, regenerated by `adrpy log` on every write ([ADR0003V01R00](ADR0003V01R00-decision-log-entries-separate-human-reviewed-judgment-from-tool-executed-mechanics-via-a-future-adrpy-log-command.md)); the decisions folder has none.

## Context and Problem Statement

Where does a readable list of a repository's decisions come from, and how is it kept true?

## Decision Drivers

* The list must never go stale: a page that says a decision is Proposed after it was accepted is worse than no page.
* It must come from the same data `explore` reads (file names and headers), never from hand-written prose.
* No new command: every command adrpy-tui shows needs a screen of its own (its ADR0004V01R01's coverage test), and an index nobody asked for should not need a step of its own either.
* The page must not be taken for a decision, or for a file to migrate, by any command that scans the decisions folder.
* A decision already written must not be lost, or reported as failed, because the page after it could not be written.

## Considered Options

* No index: `explore` stays the only list.
* A command, `adrpy index`, run when someone wants the page.
* The page regenerated by every command that writes a decision, as `adrpy log` does for the decision log.

## Decision Outcome

Chosen option: **the page regenerated by every command that writes a decision**, because it is the only option that keeps the page true without anyone having to remember a step.

1. **File.** `<folderadr>/INDEX.md`, written with the same atomic write as every other file (ADR0001V01R00), deterministic (no timestamp), so an unchanged repository rewrites it byte for byte.
2. **Who writes it.** `init`, `new`, `approve`, `reject`, `undo`, `version`, `revise`, `supersede` and `migrate`, at the end of a successful run, through one function (`core/adr_index.py`). A repository created before this exists gets its page at its first write.
3. **Content.** A title, a line saying the page is generated, and one table of every decision ordered by number, version and revision: the file (a link), its title, its state with the repository's own label, scope, domain, the created and changed dates, and the successor when there is one. The column names are the repository's header labels, so the page reads in the repository's language.
4. **Never a decision.** `check`, `explore`, the consistency rules and `migrate` leave `INDEX.md` out of the decisions folder's files, as they already do for the decision log's own `INDEX.md` and `CYCLES.md`; a legacy `migrationpattern` never adopts it.
5. **A failure to write it is a warning, not a failure.** The decision the command wrote stays written and the answer says the index could not be updated; the next successful write brings it back in step.

### Positive Consequences

* The repository carries its own list of decisions, true after every command, readable anywhere Markdown is.
* No new command, flag or config field.

### Negative Consequences

* Every write also changes `INDEX.md`, one more file in each commit that touches a decision.
* A decision edited by hand, outside adrpy, is not reflected until the next adrpy write.

## Pros and Cons of the Options

### No index

* Good, because nothing new is written.
* Bad, because the only list needs the tool, and none is readable where the repository is browsed.

### A command, `adrpy index`

* Good, because the page is written only when asked for.
* Bad, because it goes stale the moment a write happens without it, and adrpy-tui would need a screen for it.

### The page regenerated by every write

* Good, because it can never be older than the last write.
* Bad, because every write command gains one more file to write, and one more failure to report.
